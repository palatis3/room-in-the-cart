# Room in the Cart

Native iPhone implementation of Foundation 2.1, with an account-free pack comparison and shopping list, meal planning, pickup workflows, recovery tools, and connected household and membership modules. The [current acceptance map](docs/CURRENT-ACCEPTANCE.md) tracks verified behavior and remaining release work.

Open [RoomInTheCart.xcodeproj](ios/RoomInTheCart.xcodeproj) in Xcode, choose **RoomInTheCart-Release**, select an iPhone simulator, and run. The simulator preview runs without a signing team, account, or backend setup. Use **RoomInTheCart** for Debug development. The deployment target is **iOS 17.0** and hosted CI builds with Xcode 26.3.

The app has Shop, Dinners and Records tab roots. Shop includes staged list import, distinct manual/meal/protected contributions, exact comparison, checkout review and pickup reconciliation. Meals retain stable identities and dates; reviewed dinner planning and optional on-device capture are integrated in source, with additional acceptance work underway. Records supports comparison reopen and scoped encrypted export/recovery into isolated workspaces. Household and StoreKit membership adapters are integrated in source, with role-aware routing and a local device-owner gate after shared use. This is not a claim that every launch requirement or live provider flow has passed acceptance.

In **Shop**, open **List order and aisles** to arrange the active items, or **Large-print list** for a printable copy. **Dinners** can start the first pickup and prepare an editable meal idea from an original pattern. Saving an idea to the dinner library and applying its ingredients to a pickup are separate decisions. In **Records**, connected adults can review entered prices and period budgets. Choose the household overview for a period that includes more than one permitted shop. Optional pickup feedback is off until enabled in Settings.


In **Records → Family decision history**, review the pickup evidence and record what your household observed. The cook handoff can save a dated copy and separately record who received it and who acknowledged it. **Review prior staples** lets a named Household shopper revisit the store and purpose before adding a need to a fresh list.

## First task

1. Open **Shop → Compare packs** and enter 12 wraps.
2. Enter two quotes. Pack A has 8 wraps for $3 and Pack B has 6 for $2. Set an optional $30 item limit.
3. Tap **Compare enough food**. Either quote needs two packs, costing $6 for A or $4 for B. Blank quantities and prices stay unresolved.
4. Tap **Save comparison** and wait for **Saved on this iPhone**. Relaunch, open **Records**, and choose the saved comparison.

Costs and limits apply only to the item. They exclude other groceries, fees and taxes. There are no network calls in this flow and no sample household data on a fresh install.

## Build and verify

Requirements: macOS, Xcode with an installed iPhone simulator, Python 3.9+, Node 22.23.4/npm. The handoff reference verifier separately requires Python 3.13+.

```sh
bash scripts/check.sh
```

The script checks generated files, runs Swift package and web/service tests, and verifies the Debug simulator bundle. Project files and assets are committed. Regenerate the project when adding or removing Swift files.

Run the app model and UI tests through the **RoomInTheCart** scheme’s Test action or use the command below. Get the simulator UUID from `xcrun simctl list devices available`. Use the **RoomInTheCart-LocalStoreKit** scheme for the simulated billing cases.

```sh
RUN_UI_TESTS=1 IOS_SIMULATOR_DESTINATION='platform=iOS Simulator,id=YOUR_SIMULATOR_UUID' bash scripts/check.sh
```

Tests use a separate DEBUG-only workspace and typed input, never the user's normal comparison database. UI tests exercise persistence, unknown values, Spanish, large text, dark appearance, and automated accessibility checks. Automated audits do not substitute for a human VoiceOver/device session.

## Structure

- `ios/Packages/CoreDomain`: exact rational quantities, checked USD cents, ledger contributions, checkout, pickup policy, reviewed dinner planning and pack-selection evidence.
- `ios/Packages/LocalStore`: versioned SQLite comparison and ledger databases, serialized writes, immutable revisions and scoped comparison tombstones. Whole-ledger retirement uses durable deletion intent and replay-safe cleanup.
- `ios/Packages/HouseholdClient`, `ios/Packages/RecordArchive`: scoped network contracts/retry handling and encrypted recovery validation.
- `ios/Packages/DeviceSurfaces`, `ios/Extensions`: isolated selected-text inbox, generic widget routes and local reminder primitives. App composition is undergoing integrated testing.
- `ios/App`, `ios/Features`: native composition and comparison, ledger, pickup, records, household and membership views/models.
- `shared/contracts`: fictional pack vectors and accepted Foundation semantic color tokens.
- `service`: PostgreSQL/RLS-backed household and billing service, verified provider sessions, narrow projections and a reusable runtime/HTTP adapter. Browser authentication is implemented but provider enablement is deliberately off; new privacy/maintenance migrations require separate deployment review.
- `web`: invite, own-request and narrow helper clients with reviewed requests and identity-bound retries; the deployed client correctly reports unavailable email sign-in until provider configuration is enabled.
- `.github/workflows/ci.yml` runs on main pushes, pull requests and manual dispatch. Source checks, Swift package tests with coverage, the simulator build, unsigned iPhone Release validation and Swift CodeQL run independently. PostgreSQL and web/service checks use disposable data.

## Continuous integration

The simulator build enumerates the compiled tests and assigns every enabled case once. Disabling an ordinary compiled test fails planning; the separate StoreKit suite is the only allowed exclusion. Model tests use one job. Ten smaller UI jobs share the compiled app, with at most five test jobs running concurrently. The planner uses observed hosted durations where available, scaled local durations for other existing cases and a default estimate for new cases. Each job verifies the exact executed test identities and count, rejects missing or skipped tests, and retains its result bundle, screenshots, logs and timing. The test step has a 40-minute limit and the job has a 55-minute limit. A runner killed before connecting can retry once. An executed failing test fails its job. The final **CI gate** rejects failed, cancelled or skipped prerequisite jobs, including any failed test matrix member.

GitHub Free currently permits five concurrent macOS jobs and twenty total jobs. Independent macOS build and analysis jobs share that account limit with the test jobs. Linux source, backend and security checks use the total concurrency allowance. The new topology still needs hosted timing and a complete passing run. [GitHub runner limits](https://docs.github.com/en/actions/reference/limits#job-concurrency-limits-for-github-hosted-runners), [workflow results](https://github.com/palatis3/room-in-the-cart/actions/workflows/ci.yml)

macOS jobs use the standard Apple Silicon `macos-15` image with Xcode 26.3. The latest complete UI matrix supplies 49 completed XCTest pass durations for balancing. Its failed case is excluded and retains a conservative estimate. Runtime-warning acceptance remains a separate check. With these weights, the ten groups each contain about 14 minutes of estimated test execution, excluding build, setup and queue time. This is a scheduling estimate; the updated assignment still needs hosted validation and does not prove an overall speedup. These standard runners are free for this public repository. The **Security checks** workflow scans TypeScript/JavaScript and GitHub Actions with CodeQL. Pull requests run dependency review, failing on newly introduced high or critical dependency vulnerabilities. Dependency review requires the repository's dependency graph. Swift CodeQL uses a separate build of the same arm64 iPhoneOS Release sources with optimization disabled. The ordinary optimized Release build and its metadata check remain independently required; the analysis build is not a distribution artifact. The first split hosted run passed both jobs, with nonempty Swift extraction and successful analysis. Its traced build took 27 minutes 54 seconds, so this remains a substantial independent lane. [Hosted analysis evidence](docs/evidence/native/ci-candidate-codeql-20261105.json) · [GitHub CodeQL](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-code-scanning) · [dependency review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review)

Use **Pre-release regression checks** on the candidate branch before an App Store submission or update. It runs the ordinary checks together with the additional suites below. Its final gate rejects failures, cancellations, skipped prerequisite jobs, missing performance baselines, incomplete CodeQL language coverage for the exact commit, serious open source findings, and high/critical vulnerabilities anywhere in the dependency lockfiles. The compiled Release app must also have production support/policy URLs and an Apple subscription product ID. The branch must still point to that candidate when the gate finishes. This workflow does not sign or upload an app.

Third-party workflow actions are pinned to full commit hashes. Dependabot checks Actions and both npm projects weekly, groups minor/patch updates and limits open version-update pull requests. Updates still require review and CI; there is no automatic merge. Security alerts are separate from this weekly version-update schedule. [GitHub dependency updates](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)

Source checks also verify that `.node-version` names a published, supported stable release at or above its major version's latest security release. Both projects' manifest and lockfile engine constraints must agree with the pin. Missing official metadata fails the check. This catches runtime security updates that dependency-lockfile audits do not cover; it does not update the runtime automatically. The Node 22.23.4 upgrade passed web, service, PostgreSQL operations and real Swift HTTPS tests locally. [Runtime validation](docs/evidence/native/node-runtime-security-20261105/validation.json)

Repository secret scanning and push protection are enabled and independently verified. Push protection checks supported credential patterns before accepting future pushes; it does not detect every possible secret. The initial alert query returned no open alerts, which is not proof that a complete historical scan has finished. Ordinary, fixture and performance jobs inspect structured XCTest runtime warnings. Xcode 26.3 can omit them from its summary, so the verifier reads every selected test's result tree and detailed result, including cases with no warning marker. A clean tree must match a valid clean detailed result. New messages, unexpected counts or unreadable evidence fail validation. One existing UIKit reparenting message has a narrow allowance for two named tests on the observed simulator, with occurrence caps of two and one. Its origin remains unknown and each occurrence is reported; there is no blanket UIKit exemption. Actual artifact replays and negative mutations pass locally. Removing only a warning marker reproduced a false zero in the earlier checker; the full-detail verifier rejects it. Reading all 565 model details added about 31 seconds locally, and the UI shard checks added less than one second each. Its next hosted invocation remains pending. Records Media runs the same strict checks but publishes a separate report containing only its fixed selector, known result status, bounded counts and an optional source line validated against the exact test file. Screenshots, recovery keys, raw assertions and warning text stay on the temporary worker. Invalid evidence or a failing underlying test cannot produce a passing report. Positive and negative saved results and private-field mutation tests pass locally; hosted validation is pending. [Report validation](docs/evidence/native/records-media-ci-20261105/safe-report-validation.json)

Performance uses the dedicated **RoomInTheCart-Performance** scheme with an optimized Release app, no debugger, coverage or sanitizers. Measurement validation requires five finite XCTest samples for launch/scroll/memory. After relaunch, the UI confirms the final checked row in history; independent SQLite readback verifies the exact 500-row state and all 20 checked identities. Missing measurements cannot count as a pass. Simulator scroll runs explicitly report when frame-hitch metrics are unavailable. UI search/checkoff round trips include XCTest input and idle waiting; they are not frame-latency measurements. [Apple performance testing](https://developer.apple.com/documentation/xcode/writing-and-running-performance-tests), [animation metrics](https://developer.apple.com/documentation/xctest/xctossignpostmetric/scrollinganddecelerationmetric)

Run **iOS Release performance** manually with baseline enforcement off to collect calibration. Strict pre-release runs require reviewed limits in `scripts/ios_performance_baselines.json` matched to the exact Xcode, simulator model, OS/build and architecture. Calibration does not automatically become a baseline. The initial limits below follow two complete hosted measurements of the same Release products on Xcode 26.3 / iPhone 17 / iOS 26.2 build 23C54 / arm64. They allow roughly 25–33% above the larger observed result, including the approximately 10% memory variation between runs. These are simulator regression limits, not physical-device responsiveness targets. The next candidate passed strict launch and rendered interaction checks, while its first scrolling attempt correctly failed because XCTest omitted the required duration series. The original failure remains an instrumentation reliability issue; there is no automatic retry-until-green policy. [Latest performance evidence](docs/evidence/native/ci-performance-strict-20261105/validation.json) Changing Xcode or the simulator requires new reviewed calibration. Investigate a regression before adjusting its limit; never raise limits automatically to make a candidate pass. Signed memory deltas remain diagnostics because allocation and cleanup make them unstable. The maximum-peak cap adds 33% above the larger observed maximum and catches a single reported scroll-window spike that the median could miss; it does not observe every allocation throughout the app. No run emitted animation-hitch samples, so these limits do not certify frame smoothness.

Ordinary CI exercises English, Spanish, large text, dark appearance, automated accessibility audits and native Reduce Motion during a share/cancel/relaunch flow. It also verifies that a corrupt recipe import preserves existing dated dinners and portion bindings across a real-store restart. The checkout property test independently prices every billed increment for 480 seeded quotes to catch rounding and stacked-fee discontinuities. Package coverage identifies untested logic; a percentage alone does not establish correctness. [Apple coverage guidance](https://developer.apple.com/documentation/xcode/determining-how-much-code-your-tests-cover)

For a behavior bug fix, preserve the failing scenario and add or strengthen a focused regression at the layer that can reproduce it. Check the saved state and permissions as well as the visible result, including cancellation or restart when relevant. Record the original failure and the corrected result separately. A test-driver correction must retain its product assertions; increasing a timeout, skipping the case or relaxing a performance limit does not establish a fix. New random or generated cases should retain their seed and failing input so the failure can be reproduced. Run the full pre-release workflow on the final candidate for each App Store release or update; an earlier commit's green result does not certify a later build.

Before distribution, validate the actual signed candidate with `scripts/check_built_app.py --configuration Release --require-release-metadata`, real-device accessibility and animation review, sandbox/TestFlight billing, and live-provider acceptance. The microphone permission probe requires a fresh simulator with native prompts and an available on-device recognizer and remains a separate check. These requirements are not satisfied by fictional household fixtures or local StoreKit. [Apple diagnostic tools](https://developer.apple.com/documentation/xcode/diagnosing-memory-thread-and-crash-issues-early), [StoreKit testing](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)
