# Private reports and sender blocks

The feature covers received household request wording, shopper clarification, cook projections, helper corrections and shared dated cook copies. The household service verifies the current authenticated device, household, granted projection or own-request scope, exact record revision, field and original sender. Private offline entries stay on the device. Existing grant expiry, consent withdrawal and revocation still apply.

The native and companion clients request the safety capability using `X-Shared-Content-Safety: 1`. Show safety actions when the service advertises `shared_content_safety`. A child can report a question on their own request. An invited cook can report a field in their current instruction, including in a read-only grant. An assigned shopper can report contributor wording, incoming suggestions or another shopper’s dated copy in their authorized shop.

## Household action

`POST /v1/households/{householdId}/moderation/actions` uses the existing authorized-device or session credentials. Browser mutations require the same origin and CSRF protections as other commands. Supply a new UUID `clientKey` for each reviewed action. Reuse it for an uncertain retry with precisely the same action, content reference, disclosure choice and scope.

| Field | Supported values |
| --- | --- |
| action | `report` or `block` |
| source | Opaque record UUID `id`, displayed positive integer `revision`, `kind`, `field` and, for an instruction row, zero-based `index` |
| reason | Required for a report. `harassment`, `unsafe` or `other` |
| text | Optional for a report. The user affirmatively selects the exact displayed field. An immutable dated copy supports an exact contiguous excerpt up to 1,000 characters. Blocks omit text. |
| response | `receiptId` and `status` (`received` or `blocked`). A receipt acknowledges the submitted action. |

| Source kind | Record and accepted fields |
| --- | --- |
| request | Request ID and revision, `item` or `amount`, visible to its assigned shopper |
| clarification | Request ID and revision, `question`, visible to its contributor |
| instruction | Recipient’s live grant ID and revision. `shopLabel` or an item’s `label`, `amount`, `unit` or `action` |
| suggestion | Proposal ID and proposal revision, `correction`, visible to its authorized reviewer |
| cookCopy | Dated copy ID and immutable version, `text`, visible to its assigned shopper |

Current scope or source loss returns the service’s unavailable result. Changed wording returns `stale_base` when the person still has access. A legacy message with unknown authorship remains reportable. Blocking it returns `sender_unavailable`. The service never substitutes the current shopper for an earlier sender. A personal block follows the sender within the household. Operator suspension follows the verified account across memberships. Operator removal follows the selected field when other details change, including a changed quantity on a reported item or a cook instruction moved to another row. An exact correction receives a new field generation. An explicit next-shop carry keeps the original item and amount generations independently. These internal numeric identifiers contain no message text. A later edit does not change the author recorded on the original report. Underlying order quantities and financial history keep their meaning.

## Responding to a private report

Provision a separate individual database login belonging only to the NOLOGIN `ritc_moderator` group for a designated operator. Keep that credential in the operator’s managed secrets and outside the customer service, scheduled heartbeat and mobile application. Use a verified TLS connection under that login. No public moderation management endpoint exists. The application role has neither access to the operator queue nor permission to read case excerpts.

1. Check non-content queue age and expiry with `SELECT * FROM ritc.moderation_workload()`. Escalate aging cases against the staffed response timeline. Inspect the oldest 50 open reports with `SELECT * FROM ritc.moderation_queue()`. Each result contains a random case ID, time and expiry, selected field, reason, sender-known flag and the excerpt the reporter chose. A blank excerpt is an intentional privacy choice. The queue omits member names, reporter identity, email, household roster, budgets, full recipes and adjacent lines.
2. Bind the case UUID and reviewed decision as independent SQL parameters in `SELECT ritc.moderation_resolve($1,$2)`. Use `dismiss` to close a concern, `remove` to suppress the current wording and `suspend` to remove it and restrict the known author. A different resolution after adjudication is rejected. A repeated identical resolution is idempotent. The database records the time and individual login. There is no automatic sanction from the report count.
3. Verify the effect through the appropriate shopper, contributor or cook view. Test that an unrelated household cannot see the report and that the blocked wording stays absent after refresh. Offline copies shared outside the service remain under their recipient’s control.
4. Run `SELECT * FROM ritc.moderation_prune()` under operator authority on the approved recurring schedule and before opening any restored database to users. Escalate any nonzero `expired_unreviewed` count to the designated operator. Record only the run time and aggregate counts in routine operational logs. Evidence and reporter-linked receipts expire according to the reviewed deployment’s retention interval. Blocks and removal decisions persist to enforce the user or operator decision. Account erasure clears report and block links to the affected member.

## Activation and response ownership

Production defaults to disabled. Enabling it requires `SHARED_CONTENT_SAFETY_ENABLED=true`, a nonempty `MODERATION_OPERATOR_APPROVAL` reference and `MODERATION_RETENTION_DAYS` set to the approved positive interval of at most 365 days. Changing the retention interval affects newly accepted actions.

Before activation, Venture House Group LLC designates the staffed queue owner and backup, records the response and escalation timelines, approves access and retention including backups, verifies the public support inbox, and reviews disclosures for family and child data. Run a synthetic exercise from both languages on the scoped iPhone and browser clients. Verify a report with and without an excerpt, an organizer as the reported sender, an unknown legacy sender, a lost reply, a cross-household rejection, an actual resolution, expiry and account erasure. Confirm the monitoring schedule alerts an accountable operator before an unanswered case expires. Record completion against the build, service and migration in the release checklist.

The implementation does not assign Apple an enforcement deadline. Apple requires ongoing filtering, a way to report concerns, timely handling, blocking and published contact information. [Apple App Review Guideline 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)

## Adult pickup pilot

Migration 069 adds two independently gated iPhone workflows. Neither gate is enabled by default. A live, enrolled adult member opens the selected household and shop. Child accounts, helper grants and restricted own-request web sessions cannot open the new endpoints.

**Last call.** Set `ADULT_LAST_CALL_ENABLED=true` and record the owner's decision in `ADULT_LAST_CALL_APPROVAL` to activate the in-app pilot. The assigned shopper sets a future cutoff within seven days. The first publication records current adult contributors other than the shopper. A retry with the same cutoff returns the same invitation. Changing the cutoff updates its revision and keeps a prior pass, send or mute. New members receive no historical invitation. Leaving the household or losing contribution permission clears the recipient's entry. A change of assigned shopper or closure ends the invitation. No push, household roster, private item, budget or shopping activity is included in the invitation. The ordinary request command uses server receipt time to route a late participant's request to the next trip. A lost acknowledgment replays the committed request.

**Exact product.** To operate the text pilot, enable the existing staffed text safety controls and set `ADULT_PRODUCT_REFERENCE_ENABLED=true`, `ADULT_PRODUCT_REFERENCE_APPROVAL` and `ADULT_PRODUCT_REFERENCE_RETENTION_DAYS` (1 through 7). The author previews the named assigned shopper and shares a description, with optional brand, size and barcode. The service checks the request revision, shopper identity, assignment epoch and explicit consent. Editing the identifying wording, withdrawing or resolving the request, revoking the author's contribution, transferring the shop, closing the shop or departing the household clears the affected publication. An added item can retain the reference for shelf identification until its expiry or shop closure. The recipient can report the current publication or block its sender. Reporting immediately hides that publication for the recipient and opens a reason-only case under the existing moderation process. Text filters and posting suspensions apply.

**Media.** Evaluate item identification with text alone first. An approved media pilot additionally requires `ADULT_PRODUCT_MEDIA_ENABLED=true`, `ADULT_PRODUCT_MEDIA_APPROVAL` and `ADULT_PRODUCT_MEDIA_OPERATOR_APPROVAL`. Obtain separate owner approval for the comparison results, staff, review timeline, access, disclosure and backup retention. The author must choose and review a crop and its text equivalent. The service accepts only bounded RGB pixels, with no file container, EXIF, GPS, filename or URL. A maximum of eight live images per household author may await or retain approval. The assigned shopper can read the text immediately. Pixels remain private to the author and the authorized media reviewer until approved. An image replacement requires a fresh reviewed publication and decision. Opening the product screen uses authenticated, no-store reads. There is no public file URL, background notification or offline download workflow.

Provision a dedicated operator login in the `ritc_media_moderator` group through the approved deployment process. Keep operator credentials outside applications, client builds and the scheduled worker. The SQL function `ritc.product_media_queue()` returns up to ten pending publications, each with an opaque publication ID, expiry, description, dimensions and pixel bytes. On an approved workstation with an interactive true-color terminal, set the dedicated login in `PRODUCT_MEDIA_REVIEW_DATABASE_URL` and run `node scripts/review-product-media.mjs` from the built service directory. Set `PRODUCT_MEDIA_REVIEW_CA_PEM` if the deployment requires its own CA. The reviewer displays one current crop and its text at a time in the alternate terminal screen. Type `approve`, `reject` or `quit`. Disable terminal recording and keep rows out of tickets, downloads and routine logs. Inspect for unsafe imagery and unrelated people, locations or sensitive information before approving. Bind the reviewed publication UUID and either `approved` or `rejected` to `ritc.product_media_resolve($1,$2)`. A true result confirms that this current, unexpired pending publication received the decision. Rejection discards its pixels immediately. The service retains the latest decision time and reviewer login with the live publication. A reported approved image returns to the media queue and stays hidden for the reporting recipient. The text moderator can separately resolve the case and suspend a sender under the existing process.

Reads and operator review stop at the configured expiry. Each scheduled operations run removes expired text and pixels in bounded batches, including after the pilot is disabled. Continue running maintenance and monitoring its cadence while rows remain. A registered quarantined restore discards all pilot references, notices and recipient responses before traffic opens. The original request remains available under its normal lifecycle. An author can make a fresh share after restore. Keep backup access restricted and honor the separately approved backup expiry. Existing captures held privately by the author and copies a recipient makes outside the application remain on their respective devices.
