# Independent deletion journal service

The app signs each journal record and sends it to this separate HTTPS service. The service stores immutable record bytes, independently verifies their signatures and dependencies, then records an admission receipt and advances the checkpoint in one PostgreSQL transaction. A persistent claim blocks the lineage if an attempt ends before it can prove its outcome. The app holds its writer key and a scoped HTTPS token. The authority holds its own Ed25519 key and database logins.

The authority and record store use different logins on one PostgreSQL primary. Keep that primary outside the app database and its restore domain. The record login can insert or read exact object versions. The checkpoint login can read objects, append admissions and advance the registered origin. Run the authority on infrastructure with a separately managed backup and recovery policy. PostgreSQL synchronous commits make successful writes wait for WAL flush. Replication durability depends on the database deployment. [PostgreSQL WAL settings](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)

## Provisioning inputs

1. As the owner of the independent database, provision the `ritc_checkpoint_runtime` and `ritc_record_runtime` groups and one unprivileged login for each. Run [the authority schema](001_checkpoint.sql) and [the recovery schema](002_recovery.sql) in order on that database. The app migration runner uses its own `migrations` directory.
2. Register the exact record store identity in `ritc_records.store`. Register the lineage and scope digest in `ritc_checkpoint.origin` with `claim` and `pending` null. The digest is `durableJournalScopeDigest(pins)` from the built service. The genesis `head` JSON follows `AdmittedHead`. Its inner head has version 1, the same lineage, schema digest and configuration ID, sequence 0, a 64-zero hash and `fenced: false`. The outer head has generation 1, authority revision 0, mode `active`, no pending operation and total bytes 0. Use one registration per lineage. Creating a new lineage requires a separate recovery and deployment decision.
3. Prepare an owner-only JSON configuration on the authority host. Its fields are `pins`, `writerToken` (32 random bytes encoded as unpadded base64url), `writerPublicKey` (SPKI PEM), `authorityPrivateKey` (PKCS#8 PEM), `checkpointDatabase`, `recordDatabase`, `listen` and `tls`. Each database object specifies `host`, `port`, `database`, `user`, optional `password`, and a CA PEM for remote PostgreSQL. `listen` contains `host` and `port`. `tls` contains the private `key` and the server `cert` chain. Preserve hostname verification on both network connections.
4. From `service`, run `npm run build` and `node scripts/journal-authority.mjs /protected/authority.json`. A healthy start emits `journal_authority_listening`. The app-side `createHTTPSJournalAuthority` takes the same pins, the HTTPS origin and its writer token, with a pinned CA where needed. Connect it to `createDurablePrivacyJournal` and the committed-source observer only in a reviewed runtime composition.

The fixture in [the PostgreSQL acceptance test](../tests/privacy-journal-pg-authority.postgres.mjs) runs the actual HTTPS executable against an independent PostgreSQL cluster. The app and worker use a second cluster with migrations 001–025. To reproduce, build the service and run the test from `service` with `TEST_POSTGRES_BIN` set to the PostgreSQL `bin` directory. It uses private temporary Unix sockets and removes both disposable clusters. It tests restart and process crash behavior on a single host with synthetic account-provider behavior.

The authority reserves the bytes and record slot for each admitted intent’s commit or rollback. A progress observation cannot consume that space. Reaching capacity stops further admission. Runtime activation still needs a capacity operating plan for future progress events, including the final outcome after provider deletion.

## Operator recovery

Fencing ends ordinary journal work for that lineage. Run this operation only for a reviewed recovery. From `service`, run `node scripts/journal-recovery.mjs fence /protected/recovery.json` to close admission and wait for in-flight source capture transactions. `recover` performs the fence if needed, verifies every persisted admission and reads the complete fenced source. It records rollback only for an admitted intent absent from that source. An absent claimed commit or a mismatched receipt leaves the lineage fenced and blocks sealing.

The owner configuration contains `pins`, `writerPrivateKey` and `authorityPrivateKey` in PKCS#8 PEM, `source`, `checkpoint`, and an existing owner-only `exportDirectory`. Each endpoint has a `connection` with the same fields as the service database configuration, plus the expected `databaseOid` and `ownerOid` as decimal strings. The connection user must own the journal origin table on its endpoint. Keep recovery credentials separate from the runtime services. The recovery seal and exact recovery object versions commit together in the authority database. The command exports `journal.ndjson`, `head.json`, and `seal.json` and can be retried against the same sealed result.

`node scripts/journal-recovery.mjs export /protected/archive.json` re-exports a previously sealed archive using `pins`, both SPKI public keys as `writerPublicKey` and `authorityPublicKey`, `sourceDatabaseOid`, the `checkpoint` endpoint, and an owner-only `exportDirectory`. It can run after source loss and uses no signing keys. An incomplete lineage requires the original fixed source or independently proven source recovery before it can be sealed.

Use the [quarantine restore tool](../PRIVACY-JOURNAL.md#restore-tool) with the signed seal and a verified pre-deletion dump. The local drill covers a real dump and replay, rejection of an incomplete or altered archive, and export after the source cluster was removed. Hosted backup and restore, retention policy and runtime activation remain separate release gates.
