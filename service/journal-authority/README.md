# Independent deletion journal service

The app signs each journal record and sends it to this separate HTTPS service. The service stores immutable record bytes, independently verifies their signatures and dependencies, then records an admission receipt and advances the checkpoint in one PostgreSQL transaction. A persistent claim blocks the lineage if an attempt ends before it can prove its outcome. The app holds its writer key and a scoped HTTPS token. The authority holds its own Ed25519 key and database logins.

The authority and record store use different logins on one PostgreSQL primary. Keep that primary outside the app database and its restore domain. The record login can insert or read exact object versions. The checkpoint login can read objects, append admissions and advance the registered origin. Run the authority on infrastructure with a separately managed backup and recovery policy. PostgreSQL synchronous commits make successful writes wait for WAL flush. Replication durability depends on the database deployment. [PostgreSQL WAL settings](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT)

## Provisioning inputs

1. As the owner of the independent database, provision the `ritc_checkpoint_runtime` and `ritc_record_runtime` groups and one unprivileged login for each. Run the [authority schema](001_checkpoint.sql), [recovery schema](002_recovery.sql), [worker capacity schema](003_worker_capacity.sql), and [successor schema](004_successor.sql) in order on that database. The app migration runner uses its own `migrations` directory.
2. Register the exact record store identity in `ritc_records.store`. Register the lineage and scope digest in `ritc_checkpoint.origin` with `claim` and `pending` null. The digest is `durableJournalScopeDigest(pins)` from the built service. The genesis `head` JSON follows `AdmittedHead`. Its inner head has version 1, the same lineage, schema digest and configuration ID, sequence 0, a 64-zero hash and `fenced: false`. The outer head has generation 1, authority revision 0, mode `active`, no pending operation and total bytes 0. Use one registration per lineage. After sealing a lineage, use the successor command to register its next checkpoint.
3. Prepare an owner-only JSON configuration on the authority host. Its fields are `pins`, `writerToken` (32 random bytes encoded as unpadded base64url), `writerPublicKey` (SPKI PEM), `authorityPrivateKey` (PKCS#8 PEM), `checkpointDatabase`, `recordDatabase`, `listen` and `tls`. Each database object specifies `host`, `port`, `database`, `user`, optional `password`, and a CA PEM for remote PostgreSQL. `listen` contains `host` and `port`. `tls` contains the private `key` and the server `cert` chain. Preserve hostname verification on both network connections.
4. From `service`, run `npm run build` and `node scripts/journal-authority.mjs /protected/authority.json`. A healthy start emits `journal_authority_listening`. The app-side `createHTTPSJournalAuthority` takes the same pins, the HTTPS origin and its writer token, with a pinned CA where needed. Connect it to `createDurablePrivacyJournal` and the committed-source observer only in a reviewed runtime composition.

The fixture in [the PostgreSQL acceptance test](../tests/privacy-journal-pg-authority.postgres.mjs) runs the actual HTTPS executable against an independent PostgreSQL cluster. The app and worker use a second cluster with migrations 001–028. To reproduce, build the service and run the test from `service` with `TEST_POSTGRES_BIN` set to the PostgreSQL `bin` directory. It uses private temporary Unix sockets and removes both disposable clusters. It tests restart and process crash behavior on a single host with synthetic account-provider behavior.

The authority checks intent capacity before opening an uncertainty claim. It reserves the bytes and record slot for each admitted intent’s commit or rollback. The deletion worker also books a persistent allowance for each target erasure and every possible new provider outcome before acting. An allowance counts against all other work until the exact event is admitted or the completed job releases its unused allowances. Provider retries that leave the recorded state unchanged use no new journal record. At capacity the worker leaves an unstarted step pending. The operations runtime emits a signed aggregate capacity observation and flags the 80% threshold. Operators still need hosted alert delivery and a reviewed capacity policy for the finite lineage.

If another writer holds an active claim, the authority refuses claim and capacity commands before the contender makes a change. The HTTPS client distinguishes this refusal from an unknown outcome. The contender can retry after the first writer finishes. A missing response after a dispatched write or an expired reservation still requires the uncertainty and owner recovery procedures.

## Operator recovery

Fencing ends ordinary journal work for that lineage. Run this operation only for a reviewed recovery. From `service`, run `node scripts/journal-recovery.mjs fence /protected/recovery.json` to close admission and wait for in-flight source capture transactions. `recover` performs the fence if needed, verifies every persisted admission and reads the complete fenced source. It records rollback only for an admitted intent absent from that source. An absent claimed commit or a mismatched receipt leaves the lineage fenced and blocks sealing.

The owner configuration contains `pins`, `writerPrivateKey` and `authorityPrivateKey` in PKCS#8 PEM, `source`, `checkpoint`, and an existing owner-only `exportDirectory`. Each endpoint has a `connection` with the same fields as the service database configuration, plus the expected `databaseOid` and `ownerOid` as decimal strings. The connection user must own the journal origin table on its endpoint. Keep recovery credentials separate from the runtime services. The recovery seal and exact recovery object versions commit together in the authority database. The command exports `journal.ndjson`, `head.json`, and `seal.json` and can be retried against the same sealed result.

`node scripts/journal-recovery.mjs export /protected/archive.json` re-exports a previously sealed archive using `pins`, both SPKI public keys as `writerPublicKey` and `authorityPublicKey`, `sourceDatabaseOid`, the `checkpoint` endpoint, and an owner-only `exportDirectory`. It can run after source loss and uses no signing keys. An incomplete lineage requires the original fixed source or independently proven source recovery before it can be sealed.

Use the [quarantine restore tool](../PRIVACY-JOURNAL.md#restore-tool) with the signed seal and a verified pre-deletion dump. The local drill covers a real dump and replay, rejection of an incomplete or altered archive, and export after the source cluster was removed. Hosted backup and restore, retention policy and runtime activation remain separate release gates.


## Successor registration and archive verification

`node scripts/journal-recovery.mjs link /protected/link.json` registers a single successor of the exact retained predecessor seal. It writes `successor.json` to the owner-only export directory. The operation can be repeated with the same inputs. The checkpoint rejects a different successor once the first link is recorded. Keep the successor writer configuration out of service until the source has been switched and verified.

The link configuration uses the export fields `pins`, `writerPublicKey`, `sourceDatabaseOid`, `checkpoint` and `exportDirectory`. It also requires the predecessor's PKCS#8 `authorityPrivateKey` and a `successor` object with its full `pins`, `writerPublicKey` and `authorityPublicKey`. The source identity and registered record store carry forward. The signed link pins the complete successor configuration, so new writer and authority keys can be introduced at this boundary.

After source loss or key retirement, run the existing `export` with `includeSuccessor: true` to recover the link with the predecessor's public keys. Preserve the reported `sealDigest` alongside the approved recovery boundary in independent custody.

`node scripts/journal-recovery.mjs verify-window /protected/window.json` reads the sealed archives in order using public keys. Set `startScopeDigest` from the trusted backup metadata and `terminalSealDigest` from the trusted final checkpoint. Keep both anchors independent of the archive files being checked. Each element of `segments` supplies `pins`, `writerPublicKey`, `authorityPublicKey`, `journalPath` and `sealPath`. Supply `incomingLinkPath` for each element after the first. The verifier reads one archive at a time and rejects gaps, altered links and key substitutions. Use the source rollover commands below to switch the live binding. Quarantine replay across the verified window remains a release gate.


## Source rollover

1. Apply source migration 028 and authority schema 004. Disable new deletion acceptance while enough capacity remains to finish outstanding jobs. Keep worker processing enabled until it finishes and acknowledges them.
2. Run `node scripts/journal-recovery.mjs seal-for-rollover /protected/recovery.json` with the existing recovery configuration. It checks the authority binding and locks the source origin before checking jobs and acknowledgements. It refuses a source with unfinished work, unacknowledged events or a restore plan. A retry can finish the seal if the process stops after fencing the source. Use ordinary `recover` for emergency fencing and export.
3. Register the successor with `link`. For the successor's `schemaDigest`, use `journalHash` of the applied `version, checksum` rows from `public.ritc_schema_migration`, ordered by `version`. Keep the successor runtimes out of service until activation.
4. Run `node scripts/journal-recovery.mjs activate /protected/activation.json`. The configuration contains the predecessor `pins`, its `writerPublicKey` and `authorityPublicKey`, the owner `source` and `checkpoint` endpoints, and `successor` containing the new pins. The tool checks the retained signed link, empty checkpoint and unchanged drained source before moving the binding and recording the link in one transaction.
5. Verify the successor observer and both runtime bindings before enabling processing and acceptance. Earlier completed receipts still use their existing tokens. Preserve the old archives and their links for backup recovery.

This path requires a drained predecessor. If the journal is exhausted with unfinished work, the source remains fenced when activation is refused. Chained replay, hosted backup and alert delivery remain separate release evidence.
