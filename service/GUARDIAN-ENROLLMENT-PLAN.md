## Proposed product flow and authority

1. An enrolled, unlocked adult guardian opens S21, reads the current operator-approved notice in their chosen language, and makes an explicit parent/legal-guardian declaration. The server creates a bounded opaque child slot, keyed to household, exact guardian member, exact live provider session/device and notice digest. Keep a child alias local until explicit consent. No live child member/device or request access exists yet.
2. A separately requested verification action persists its attempt/nonce **before** the external start call. Never hold the household transaction during a network call. Start must bind the KWS organization/product/environment, enrollment ID, initiating session and random nonce. Only opaque correlation data goes in external payloads; no groceries, child alias, household label or budget.
3. Only a configured provider's **server-authenticated** completion can record adult proof. Verify its actual official signature, configured organization/product/environment, exact pending attempt/nonce, server expiry, guardian/session/device still live and verified guardian email. A browser redirect only opens status/refresh. Deduplicate exact verified events and reject changed-body replay. A late callback cannot revive cancelled/expired/withdrawn enrollment.
4. Adult proof is **not consent or independent proof of the legal relationship**. The guardian separately presses Grant permission for the reviewed current notice and child slot. Store the guardian declaration accurately alongside adulthood proof and the approved method/policy version. The operator must approve that combined method; never label the declaration as independently established by PV.
5. A separate child-invitation action issues a bounded, single-use own-request invitation tied to the exact explicit-consent generation. The proposed contract uses a client-generated random secret retained in the exact protected intent; store only its hash, and reconstruct an exact retry's token from that same reviewed request. Never include it in logs or URLs with private text.
6. Child redemption uses a **distinct schema** with the child's own live authenticated identity and no adult attestation. It initially creates a bounded claim only. The child displays a random pairing code; the initiating guardian confirms that code before activation. A forwarded invite cannot silently bind an unintended subject. Reject existing adult principals; do not promote child principals through the existing adult-invite path. Child identity-provider account creation/sign-in must itself be covered by the approved guardian setup; do not invent an age threshold or email-based age inference.
7. Finalization transactionally creates/reattaches only the intended `member(kind=child,organizer=false,can_contribute=true)`, reuses `guardian_relationship` and a **new immutable `consent` record**, consumes the invitation/claim and issues a fresh child device credential. Bind it to that consent generation and the exact child subject/session. Continue through the existing S22 own-request DTO/command routes. A seat, guardian role or cook link grants no basket/budget access.
8. Reuse existing `revokeConsent` and `revokeDevices`, extending withdrawal to retire targeted enrollment/claim/invitation generations. Existing withdrawal conservatively revokes all current consent for that child. Keep that fail-closed behavior and disclose it. No callback, file, old device, replay window or old invitation may restore access. Reconsent/re-enrollment requires a fresh reviewed flow and new consent; never clear an old consent's `revoked_at`.

## Verified guardian email binding

`VerifiedIdentity` intentionally omits email. Do not accept a client email or read `user_metadata`, or assume a signed email claim establishes confirmation.

Recommended independent port: `GuardianVerifiedEmailSource.current(ctx, identity)`. Implement a narrowly scoped server-side lookup that requires the current household/guardian member, exact issuer/subject and live exact provider session, and returns only the current confirmed provider email. A SECURITY DEFINER function may read `auth.users.email` only when `email_confirmed_at` is present and the existing `provider_session_live` check passes; no raw auth table access should be granted to `ritc_app`. Alternatively use the authenticated provider own-user endpoint with fixed origin, bounded response and exact returned subject, but do not weaken browser session handling to obtain its credential.

[Supabase's official getUser reference](https://supabase.com/docs/reference/javascript/auth-getuser) documents an authentic server lookup; [official user model source](https://github.com/supabase/auth/blob/master/internal/models/user.go) distinguishes email confirmation. Verify the exact supported schema/endpoint before implementation. Fixtures must cover unconfirmed email, wrong subject/session, email change after proof, and spoofed user metadata. Bind a keyed email digest to the attempt; compare callback parentEmail to this authoritative email and recheck the current email before consent/final activation. Use no alias/dot normalization or arbitrary supplied email. Any normalization must be explicit and fail closed when unmatched.

## Proposed data and API work

New data should separate pending enrollment/attempt, trusted verified provider event, explicit consent action, child invitation and child claim. All need tenant RLS, bounded counts/expiry, actor-scoped operation keys and canonical payload digests. A normal client-facing runtime must not be able to stamp a provider-verification row simply by supplying a Boolean. Reuse the existing narrow server/worker privilege pattern; use a dedicated verifier execute-only role if reusing `ritc_worker` would grant unrelated erasure powers. Ordinary writers still must not receive unrestricted INSERT on `consent`/`guardian_relationship`.

The proposed `.d.ts` lists exact app-owned request/response shapes and paths. These are **our API**, not invented Epic endpoints. All guardian action routes are under `/v1/households/{h}/guardian/enrollments/{id}`. Generic adult invite redemption must remain unchanged; child claim/finish are distinct routes. Generic `POST /devices` must not bypass guardian-authorized child re-enrollment. The current production `allowChildNetwork:false` stays fail closed until real proof/notice/consent enforcement exists; no environment Boolean shortcut is acceptable.

Native S21 needs current notice/availability, explicit declaration, verification request/status, separate grant action, invite/pairing confirmation, cancellation and existing withdrawal. Child entry needs claim/wait/finish, then the existing S22 typed/reviewed entry. Separate all exact retry intents from shared basket operations. Recheck identity/scope on every awaited result; purge secrets and private drafts on sign-out, withdrawal and account erasure. The new DTOs must never include provider proof references, parent email, household budgets, rosters or other requests in the child's projection.

Minimize persisted data to opaque identities, notice/method versions and digests, exact coded actions, provider transaction/event references, keyed email digest and timestamps. No ID documents, card details, biometrics, birth date, raw provider payloads, voice or grocery text belongs in verification evidence. Expired setup data, credential material and provider-event retention require the operator's actual policy and the operations worker; do not invent legal retention periods. Existing backup/helper exports must continue excluding consent, provider proof and live access.
