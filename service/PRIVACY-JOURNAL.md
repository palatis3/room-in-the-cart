# Local privacy journal and quarantined replay

Migration022 adds a local operational journal boundary. It supplies no production policy, provider gateway, signing key, origin registration, email, deployment, or scheduled erasure switch. The deployed operations handler remains privacy-cleanup-only. The original001–022 rehearsal and earlier001–020+candidate022 evidence retain their historical source scopes. The current [full001–023 rehearsal](../docs/evidence/b11/privacy-journal-full23-20261103/README.md) passes fifteen local SQL/HTTP/journal/restore checkpoints, including guardian enrollment and device fences. The separate [integrated application suite](../docs/evidence/b11/integrated-backend-20261103/validation-summary.json) passes175 cases with actual Swift and web wire clients. Neither result establishes independent remote durability or hosted deployment.

Deletion acceptance now requires `provider`, numeric `policy`, and an injected `PrivacyJournalPort`. Preview remains usable and reports unavailable without all three. Recent signed authentication, exact live provider session, adult scope, provider availability/Apple gate, and all explicit responsibility checks precede acceptance. A journal is never an alternate authorization route.

`PrivacyService` opens its normal application-role transaction, obtains the SQL-resolved event, waits for the trusted port's signed/fsynced external intent, then commits. The port's separate fixed source-owner connection resolves that exact committed event, appends/fsyncs the commit observation and independently pinned checkpoint, then acknowledges SQL. Only then does the service return202 or permit ordinary worker eligibility. A commit or durability error returns no acceptance success. The original client-held status capability can recover a committed request; plaintext capabilities, JWTs, email, grocery text, provider/session credentials and raw Apple originals never enter the journal.

Source target, retry and completion transitions create immutable outbox records. `PrivacyMaintenance.run` requires the same port, acknowledges target progress before a provider call and completion before reporting success. SQL hides complete/provider-complete and blocks cleanup while required records remain unacknowledged. `cleanup()` remains usable without a journal and cannot claim/erase a pending job. Replay jobs are excluded from ordinary claim/finish.

## Private observer and worker recovery

Migration 024 adds a private observer bound to a registered source, database, lineage and login. Its SQL wrappers check effective privileges before reading exact committed events. The Node adapter verifies the independent authority receipt before sending an acknowledgement. Migration 024 creates the interface. Provisioning the login, reviewing its effective privileges and registering the source are separate owner steps.

An explicitly configured worker first claims committed events that still need acknowledgement, including events from completed jobs. The reconciliation lease expires after 30 seconds and grants no authority to erase or finish a job. The worker uses one absolute deadline for the run. Acknowledging an existing outcome preserves its original record identity. A lost response to a dispatched commit can leave an uncertain result for the next recovery attempt.

The dedicated observer fixture requires the existing reviewed local fixture roles and PostgreSQL on `/tmp:55432`. Build the service, then run `TEST_JOURNAL_OBSERVER_ROLE=ritc_guardian_test_verifier node scripts/test-privacy-journal-pg-source.mjs` from `service`. It applies migrations to two disposable databases and removes them on exit. Local SQL and observer coverage uses synthetic keys and simulated remote authority, storage and provider behavior. See the [local test record](../docs/evidence/b11/privacy-observer-worker-20261104/validation.json).

The independently hosted service implementation uses a dedicated PostgreSQL database and the scoped HTTPS protocol. Its acceptance test runs the existing app and worker on a separate source cluster and checks exact SQL acknowledgement against the retained receipts. ## Local writer

`createLocalPrivacyJournal` in `src/privacy-journal.ts` takes a dedicated fixed owner source pool, pinned lineage/schema/configuration ID/key ID, owner-only key file, owner-only journal directory and a separate checkpoint path. The request service still uses its non-owner application pool. The local synthetic harness is explicitly a trusted owner/signer process. Neither application nor maintenance roles receive raw journal/ack/plan/receipt rights or private helper execution. No supported CLI signs JSON or accepts a target list.

The append file is canonical, bounded, strict UTF-8 NDJSON. Each Ed25519 record binds sequence, previous hash, event digest/type and source identity. Startup verifies all signatures, transitions and the exact independent checkpoint before writing. A valid early prefix, changed branch, unknown key/configuration, duplicate/unknown fields, unresolved intent or uncheckpointed tail cannot produce a verified restore. A rollback is terminal.

Normal mode refuses a fenced source or an uncheckpointed tail. `mode:'recover_fenced'` is an explicit owner recovery operation: the source must already be fenced, each tail transition must resolve against immutable source SQL, and unresolved intent absence is usable only after the source fence has excluded prior acceptance transactions. It cannot accept new requests. Source fencing is monotonic. After a genuine process death the exclusive writer lock requires an operator to confirm the old process is gone before removing that one owner-only lock; the tool never removes another writer's lock automatically. No source evidence or unknown head means quarantine, with no inferred rollback.

## Restore tool

`scripts/privacy-journal.mjs verify|plan|replay|gate OWNER_CONFIGURATION` requires an explicitly named newly owned local quarantine database, exact destination OID/owner, a hash-pinned dump, an independently supplied fenced head and pinned public key/source identity. Configuration, dump and operational files are owner-only. `verify` checks the entire journal and strict target/effect schemas before staging. Node verifies the Ed25519 signatures. The SQL registration function runs only through the trusted owner.

For an independent archive, include `authoritySeal` with `path`, `pins` and `authorityPublicKey` alongside the usual writer `trust`, `headPath` and `journalPath`. Both `destination` and `worker` specify the same `database`, `oid`, `socketDirectory`, and `port`, with distinct `user` values. The database name must match `ritc_quarantine_` followed by 8–32 hex digits and the live destination must have a different OID from the sealed source. Restore the pinned dump before running `plan`. The replay worker requires the existing separate worker role. The legacy local rehearsal format retains its fixed `/tmp:55432` and fixture identities.

Migration 025 aligns the restore projection with the verified archive. The signed journal is bounded at 10,000 records and 32 MiB of canonical bytes. SQL accepts its committed-event projection with up to 10,000 events and a 64 MiB JSONB text ceiling to cover formatting expansion. The source emitter, observer and restore input all retain the 1 MiB limit for one payload. The independent authority keeps one slot and enough bytes for a commit or rollback for every unresolved admitted intent.

Migration 026 adds a lease-bound worker probe and keeps only changed pending outcomes. Before erasing a target, the durable worker reserves an allowance for the largest permitted target record. Before calling the provider, it reserves completion capacity and space for any new pending outcome. The independent authority persists these allowances by job and kind. Admission spends the exact matching allowance in the checkpoint transaction, while a lost source acknowledgement can retry the already admitted receipt. A refused new intent leaves no uncertainty claim, so existing work can spend its reserved slots. The legacy local writer continues to support isolated fixtures. Production still needs the durable runtime configuration and capacity monitoring.

`plan` calls an owner-only SQL registration function after complete preflight. It rejects conflicting jobs, target identities, guardian evidence and responsibility preimages before the first mutation. It preserves original hashes/deadlines and exact accepted before/after effects. An absent whole household/target produces `absent_no_effect`, with no invented member or identity search. Partially missing targets whose still-present household effects cannot match are unsupported and stay quarantined. Backups before lineage/capture or outside the exact recorded preimage cannot be certified. Historical jobs are never backfilled with invented authority.

`replay` uses the separate non-owner worker, a persisted run ID and a fresh lease; callers never choose a target. The next original target runs through the full existing eraser chain, including immutable history and019 cleanup. Erasure and its digest-bound receipt commit atomically. A committed receipt prevents repeated revision changes. Original adult identity markers block restored provider sessions; browser ciphertext is removed by exact original identity hash, and only exact source retired-purchase hashes are imported. A binding changed after registration still fails at the worker boundary.

The019 close trigger preserves a recorded close time only inside the original owner plan transaction, using a private immutable context bound to destination/run, full transaction ID, session-user OID and exact signed old/new shop tuple. Outside that exact context, the original clock behavior applies. GUCs cannot authorize an override. Application/worker roles cannot create/read the context; an old context cannot authorize a later transaction.

`gate` can permit a local synthetic probe only after every exact target has a matching receipt, original markers/browser checks pass and the pinned bundle/head still match. It reports `productionReady:false` and `providerReconciliationRequired:true`. Restored jobs remain pending with no provider/completion timestamp. Replay has no provider call and never invokes `privacy_finish(...,true,...)`. Historical source provider observations are retained separately.

The tested single-host fsync/checkpoint boundary does not establish independent-host disaster durability, malicious-owner resistance, production key custody, real provider deletion, an approved retention policy, arbitrary historical-backup coverage or deployment readiness. Source owner, signer and host owner are trusted. Keep source/dumps/journal/manifests and quarantine databases separate from the private signing keys.
