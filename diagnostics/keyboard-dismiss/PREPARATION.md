## Instrumentation

Every diagnostic import, property, observer, call and helper is under `#if DEBUG && KEYBOARD_DISMISS_DIAGNOSTIC`. Ordinary Debug, Staging and Release exclude them. The helper additionally refuses to log without the existing `--ui-testing` launch argument. No test-source or launch-environment forwarding change is needed. A future diagnostic build would add just `KEYBOARD_DISMISS_DIAGNOSTIC` to the original ordinary Debug condition `DEBUG`; contributor fixture conditions must not be substituted.

The unchanged `field = nil` is surrounded by synchronous Done entry/exit records. Focus observation records enum transitions, including changes between two non-nil fields. Keyboard will/did-hide notifications discard their argument without reading object, userInfo, geometry, duration or curve. They are process-wide notifications observed only while this view's SwiftUI subscriptions exist, not proof of a particular field's dismissal. Scene observation requests an initial snapshot and subsequent changes; equal old/new values can be the initial snapshot or reinstallation, not a transition. No observer changes focus or scene.

All records use OSLog subsystem `dev.roominthecart.urgentkeyboarddiagnostic`, category `events`, info level. Payload is fixed event name, process-local sequence, monotonic `systemUptime`, and fixed focus/scene enum codes. No field contents, labels derived from user input, household identifiers, UUIDs, model reads, notification payloads or app file writes enter the logging API. OSLog's envelope can include process/thread IDs for process correlation; these are not household identifiers. Sequence resets on a new app process. Equal monotonic values are permitted; sequence orders records in that process.

| Event | Applicable structural fields | Meaning |
|---|---|---|
| done.enter / done.exit | focus | Handler entry and return of the original synchronous focus write; exit is not keyboard completion. |
| focus.change | previousFocus, focus | SwiftUI-observed enum change; rendering may coalesce intermediate writes. |
| keyboard.willHide / keyboard.didHide | none | Received UIKit notification; no attribution to a particular field or scene. |
| scene.observe | previousScene, scene | Initial scene snapshot or observed scene change. |

Focus codes: -1 not applicable, 0 none, 1 food, 2 meal, 3 required, 4 available. Scene codes: -1 not applicable, 0 active, 1 inactive, 2 background, 3 unknown future case. Inapplicable fields are always -1. Schema should reject extra fields and invalid event/field combinations without retaining malformed raw text in derived reports.

The logger is main-actor isolated. UIKit keyboard callbacks enter `MainActor.assumeIsolated` synchronously, relying on UIKit main-thread notification delivery; there is no queue hop or Task. The diagnostic view modifiers exist only in the opted-in build and follow SwiftUI view lifetime. The onReceive closure never retains a Notification. Full iOS integration typing and runtime callback isolation remain unverified in this preparation.

There is deliberately **no heartbeat, polling or timer**: periodic work could perturb precisely the idle/quiescence state being investigated. Consequently event silence cannot measure main-thread responsiveness or prove a hang. Logging, view observation and notification subscriptions can still alter timing. No animation, transaction, timeout, accessibility, hit target, responder API, gesture or idle setting changes.

## How the evidence could discriminate

A positive Done entry/exit pair proves the handler ran and its synchronous assignment returned. An observed focus transition to none plus didHide supports that those transitions completed before a later recorded XCTest wait. That would narrow investigation toward animation/quiescence accounting without proving an XCTest defect. Entry without exit, or focus-none without didHide, identifies a missing *observed* boundary only after capture limitations are stated; neither absence alone proves the app stalled there. A future timeout sample should be compared with positive event boundaries and exact XCTest activities. This patch does not sample stacks, measure render completion, count animations, or prove app liveness. The UI06 post-Done similarity motivates the path but remains outside this UrgentRepair-only coverage.
