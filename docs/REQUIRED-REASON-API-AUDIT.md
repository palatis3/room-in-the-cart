Apple lists the covered APIs and approved reasons in [NSPrivacyAccessedAPIType](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype). `CA92.1` is for app-only defaults; `1C8F.1` covers defaults shared within an App Group. The latter is not justified merely by having App Group entitlements: these surfaces exchange files/SQLite data, not shared defaults. Apple's file-timestamp list names timestamp keys and POSIX metadata functions; it does not list the four resource keys inspected above. These are source-based interpretations of the documented API list.

The app, Share and Widget are separate executable targets. The extensions link the first-party DeviceSurfaces package; it has no covered shipping API hit in this inventory. Both SQLite bridges are system-library targets, not vendored SQLite source or a bundled third-party binary. The generator places the current privacy resource in the app. Apple's [required-reason guidance](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) requires each bundle containing an executable or dynamic library that uses a covered API to provide the appropriate manifest. If later extension code adds such access, the extension's own bundle needs review.

This audit leaves the parent's [data-collection inventory](PRIVACY-DATA-INVENTORY.md) and seven collection declarations unchanged. A required-reason scan does not prove collection, tracking or retention behavior. Final release work still needs the Xcode archive privacy report, the submitted app/extension binaries and all dependency manifests checked against their actual uses. Recheck when shipping source, SDKs, dependencies or Apple's API list changes. Neither signed-device acceptance nor App Store acceptance is claimed.
