# Native import recovery validation plan

Recommend a small, scratch-only XCTest journey plus one root-owned host SQLite connection holding `BEGIN IMMEDIATE` on a dedicated synthetic simulator ledger. This exercises the existing real save-error path without modifying production code, injecting a model, changing schema, changing filesystem permissions, or constructing a saved payload. No lock, native operation, implementation or test was executed for this review; the current three-case run is untouched.

## Existing mechanisms and limits

- `ios/Packages/LocalStore/Sources/LocalStore/LedgerStore.swift:103–114,233,253–263`: saves begin an immediate SQLite transaction; the connection has a 5,000 ms busy timeout. A second writer holding an immediate transaction should prevent that transaction from starting and produce the ordinary database error. This is a source-supported proposed fault, not an already observed simulator result.
- `ios/Features/Ledger/LedgerModel.swift:184–201,226–282`: the valid candidate, exact payload, base revision and operation ID become pending before the awaited save. Generic store failure retains that pending value and sets “Could not save on this iPhone. Your entries are still here. Retry the same change.” Retry reuses the pending operation; Discard reloads durable state before clearing it. A lock acquired before shop creation/open would exercise the wrong path, so acquire only after successful setup and preview.
- `ios/Features/Ledger/LedgerHomeView.swift:218–243`: the unchanged public controls are `ledgerError`, `ledgerRetrySave`, and the localized destructive button “Discard unsaved change”; recovery controls disable while saving. `LedgerSheets.swift:29–32,96–106,123–166` supplies the new active-status placement and one disabled commit action while pending.
- Existing native UI test searches did not surface a ledger save-failure fixture or native Retry/Discard case. `ContextualNavigationUITests/testLargeTextKeepsLongNativePasteEditableAndReviewReachable` already supplies largest-text launch, native Paste, staged preview, geometry and screenshot helpers. Reuse that setup/helper pattern in a separate scratch method; do not add timing or external-fault dependencies to the normal case.
- `LedgerModelPerformanceSafetyTests/testExternalHeadRemainsAuthoritativeAfterStaleSaveAndDiscard` covers model stale-save/Discard by writing a genuine foreign revision. It is not UI recovery evidence and is less suitable for Retry-success because it intentionally changes the authoritative head.
- `LedgerStoreTests/testRevisionInsertFailureDoesNotAdvanceHead`, `testInitialHeadFailureRollsBackSnapshotAndCanRetrySameOperation`, and `testCommitFailureRollsBackBothMutationsBeforeReportingError` inject SQL triggers. That is existing package fault practice, but there is no need to alter the simulator schema for this UI check. A held transaction is sufficient and releases without modifying ledger content.

## Isolation and smallest coordination addition

Use a separately owned simulator and exact frozen candidate product, after the current run completes. Choose and record one scope: ordinary launch without `--ui-testing` targets `Library/Application Support/RoomInTheCart/ledger.sqlite`; the existing DEBUG UI launch targets `Library/Application Support/UITestWorkspace/ledger.sqlite` (`LedgerModel.swift:132–153`). Ordinary launch on a fresh dedicated installation gives the strongest ordinary-app claim. Reusing DEBUG UI scope is also valid for the shared view/store path, but must be described as that scope. Neither requires ShareProbe, App Group entitlement changes, an inbox, or a new import bypass.

The old normal-app `.build/SelectedTextSystem20261104/read-persisted-state.sh` demonstrates root resolving the installed app data container and querying ledger head/revisions; do not run it unchanged because it names a historical simulator and output directory. Reuse its path/readback approach with explicit owned identifiers and fresh evidence paths. Resolve and record the actual canonical database path/file identity; open in read/write **existing-file mode**, not a connection that silently creates a missing database. Do not change journal mode or other pragmas.

There is no located ready-made cross-process lock handshake. The minimal new test-only coordination is two acknowledged phase boundaries, carried by bounded marker files in the XCTest runner's own container (or a root-driven equivalent): `preview-ready` → host `lock-acquired`; `failure-observed` → host `lock-released`. The ordinary app never reads these files. Give the invocation a unique token; reject stale/wrong-token acknowledgements, timeout each wait, and fail rather than continuing if acknowledgement is missing. Use an XCTest predicate wait with a finite deadline, not guessed sleeps. The host transaction owner records acquisition/release UTC and monotonic times, uses `finally` rollback/close and an independent finite deadline so a failed test cannot leave the writer lock held. It must not acquire by discovering arbitrary simulator processes or touching other runs.

This coordination is a proposal, not an existing verified helper. A root-driven interactive UI check could avoid runner markers, but it must still explicitly prove lock acquisition before Add and release before recovery; wall-clock delays alone are insufficient.

## One precise journey, two bounded recovery branches

1. In the chosen synthetic workspace, use the public UI to create a shop, then stage the existing distinct-line fixture at largest accessibility text. The already-proven 500-line fixture can be reused; its full size is not required to prove SQLite failure. Record the saved baseline head/revision, row count and payload hash before attempting import. No actor or process other than this app and the transaction owner writes the ledger.
2. Ensure the single `ledgerCommitImport` is present, enabled and hittable. Scroll enough in the preview that the new top error section would otherwise be offscreen. Focus a visible preview row field and assert the native keyboard appears, without changing the valid fixture. Publish `preview-ready`; host opens the exact existing database and acquires `BEGIN IMMEDIATE` with no DML/DDL, then acknowledges acquisition.
3. Tap Add once. Wait for the exact generic save error and enabled Retry/Discard after the production busy timeout. Allow a bounded UI wait exceeding five seconds, not a changed product timeout. Assert one commit action, disabled; one error and one of each recovery action; the sheet remains open. Before any reveal gesture, record whether the error arrived in the visible content area. Then check that recovery controls can be reached through the Form without clipping or overlap by the footer/navigation/actual keyboard. At very large text, the entire status need not fit simultaneously; unobscured tappability after ordinary scrolling is the requirement.
4. Record the actual post-failure keyboard state. Disabling preview fields may naturally resign focus. Do not force the keyboard back through a disabled field or claim “recovery with keyboard retained” if it disappeared. The case still covers submission beginning with a keyboard and the resulting layout. A keyboard-retained claim needs actual observed evidence.
5. While the host still owns the no-write transaction, verify durable head/revision/payload remain the baseline. Record `failure-observed`; host rolls back/closes and acknowledges release. Keep the app alive: pending import is in memory, so terminating between failure and Retry would test a different behavior.
6. Retry branch: tap `ledgerRetrySave` once through a measured unobscured native target. Expect the sheet to dismiss via the existing callback. Terminate normally afterward and use a consistent readback to verify exactly one new revision/import batch, expected fixture identities/order/quantities, and no duplicated contributions. Relaunch and verify the imported list through public UI.
7. Discard branch, if both controls are to be validated: open a second ordinary import with a different small synthetic name and repeat the same acquired-lock failure and release protocol. Tap “Discard unsaved change” once. Expect error/Retry/Discard to disappear and the preview to remain with Add enabled; Discard clears pending persistence, not the uncommitted review sheet. Then Cancel and relaunch. Verify no second import batch, no new revision since the successful Retry branch, and no discarded name. Do not assert that Discard itself dismisses the import sheet; the current callback does not do that.

## Evidence and claims

Keep exact source/product identities, runtime/compiler, selected test, native/strict results, one-start lifecycle, lock acknowledgements/deadlines, observed screenshots/geometry, and before/after synthetic ledger projections. Distinguish build from runtime warnings. A real lock receipt plus unchanged head and successful release/Retry is evidence for this controlled contention path; the public generic error itself does not expose or prove a particular SQLite error number. This is not disk-full, permission-failure, arbitrary-I/O, VoiceOver or restart-during-pending qualification. No failure message, timeout, save gate, duplicate decision or production hook needs changing.
