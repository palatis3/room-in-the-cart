# Optional measurement privacy declaration correction

Local source review and declaration validation, 2026-11-03. This note records a bounded correction to the native manifest and implementation inventory. It is not an App Store Connect submission, published privacy policy, provider review or evidence of production collection.

The existing manifest declared seven collected data types, all for App Functionality only. Optional authenticated household measurement also evaluates reviewed pickup outcomes and paid-household retention. Apple defines [Analytics](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacycollecteddatatypes/nsprivacycollecteddatatypepurposes) to include evaluating user behavior, feature effectiveness and audience characteristics. The correction adds `NSPrivacyCollectedDataTypePurposeAnalytics` to exactly three existing entries while retaining App Functionality:

| Existing data type | Implemented use and source |
|---|---|
| `NSPrivacyCollectedDataTypeOtherUserContent` | The shopper explicitly sends three reviewed answer codes: outcome, baseline and comparison. The service retains them with the response record. See `ios/Features/Pickup/PickupFeedback.swift`, `ios/Packages/HouseholdClient/Sources/HouseholdClient/HouseholdMeasurementService.swift` and `service/src/measurement.ts`. |
| `NSPrivacyCollectedDataTypeUserID` | Consent and response records retain household/member linkage and bind the response to the current consent. See `service/migrations/019_optional_measurement.sql` and `service/src/measurement.ts`. |
| `NSPrivacyCollectedDataTypePurchaseHistory` | The tenant-scoped `measurement_willing_household` view matches existing verified Production subscription state with current explicit adult measurement consent to assess household retention. See `service/migrations/019_optional_measurement.sql`. |

This mapping applies Apple's [data type definitions](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacycollecteddatatypes/nsprivacycollecteddatatype): the answer codes are user-generated content, the retained identities identify household accounts/members, and membership purchase/subscription state is purchase history. The correction does not infer new usage telemetry categories from the feature's name. The reviewed measurement path contains no app-launch, tap, scroll or session analytics event collection. All seven existing entries remain linked to identity and not used for tracking; the required-reason API declaration and top-level tracking setting remain unchanged.

The inventory now distinguishes two flows. Local pickup feedback remains in its private local pickup and may travel only in an explicitly exported owner recovery file. Separately consented household measurement sends fresh reviewed codes and retains account/shop/week/consent metadata; it does not import those local responses, grocery text, prices or member names into measurement. Withdrawal removes responses under that consent, and account erasure removes associated measurement records. The retained-buyer view excludes withdrawn consent and noneligible subscription state. See `service/API-MEASUREMENT.md` for the implemented boundaries.

Apple's [App Privacy disclosure guidance](https://developer.apple.com/app-store/app-privacy-details/) distinguishes on-device processing from collection and requires all criteria for an optional-disclosure exception. Its Product Improvement Programs exception requires data not linked to identity. The implemented household linkage therefore does not qualify for that exception merely because participation is optional. The operator must still reconcile the final shipped build, live providers and App Store disclosures. Future child-verification provider data remains a review gate before enablement; this correction adds no speculative provider categories.

Validation: the XML property list parses and passes `plutil -lint`; semantic comparison with the pre-edit manifest confirms exactly the three Analytics purpose additions above, no added or removed data types, linked `true` and tracking `false` for every collected type, and no other manifest changes. The two Markdown files retain UTF-8 text, final newlines and no trailing whitespace. No new tests or build processes were run for these literal declarations. Frozen source/build candidates were not modified; rebuilt artifacts must separately verify the updated manifest is bundled.
