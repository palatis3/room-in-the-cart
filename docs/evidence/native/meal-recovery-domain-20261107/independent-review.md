## Verdict

No concrete source defect was found within this deliberately immutable pure-state increment. It is suitable as a reviewed domain component, subject to the integration gates below. This is not approval to expose an app Apply route, to accept S09.01, or to claim a shared recovery command exists. No corrective patch is proposed on speculative grounds.

## Checked behavior

- **Target and history.** `project` validates original meal/need identities, unique operations, nondecreasing event application times and the entire exact predecessor chain. `evaluate` checks shop, current state revision and complete current target equality. The same logical occurrence remains, while new unprotected needs and meal revisions cannot reuse historical IDs. New output demands are validated before use. Decoder calls this history validation at stored instants rather than the wall clock.
- **Protected and unrelated food.** Protected ingredient records survive exactly, including their StockNeed; nonprotected group-ID membership is preserved. Replaced IDs cannot have pinned reservation edges. Every non-target demand remains exactly equal; its allocated amount cannot decline, compared after exact unit conversion. Existing pinned lot/need edges remain equal after conversion. The ninth regression meaningfully checks 500 grams against half a kilogram and a food-stealing negative.
- **Supply.** Evidence IDs are unique and bounded; all retained lots validate, including unavailable future lots. `availableAt` cannot precede confirmation, and only currently available evidence feeds allocation. Actual receipt/source provenance and latest-observation selection remain adapter obligations. Preview does not create stock, and an agreed top-up does not add food.
- **Commitments.** Replacement keeps total servings, saved date/zone/due and all existing global exclusions. Ingredient and matched available-lot labels undergo existing exclusion validation. Required and protected needs cannot be replaced with a flexible need. Timing is separately computed; missed/unknown remaining elapsed preparation requires explicit unresolved acceptance. Repeat/extra-trip consent binds the exact request; missing consent rejects apply.
- **Replay and atomic value mutation.** An already committed operation returns only when the original request and recorded review supply/reservations match. A changed operation payload conflicts. New apply requires exact source state/current evidence, recomputes preview at the supplied instant and rejects changed coverage/timing. It appends to a candidate and validates before assigning state, so a thrown error leaves the caller's value unchanged. Current actor authorization and durable CAS remain outside the engine, including on replay.

## Concrete gates for app/service integration

1. **Do not rewrite the immutable baseline.** `originalMeals` and `outsideDemands` are the historical basis for replaying every event. The API has no legitimate operation for adding/removing another commitment, changing its protected state or moving a recovered meal's date. Reconstructing state with a newer outside-demand array underneath old events could retrospectively change validation/allocation or leave a stale baseline that omits new obligations. A live adapter must compare its complete current meal/need basis and block a stale review. To keep the ordinary app editable, implement explicit typed context/calendar revisions before claiming these concurrent routes are supported; keep domain-v1 history immutable. The peer confirms this is the next planned domain addition.

2. **Retain full source semantics in adapter provenance.** RecoveryMeal contains total servings, group IDs and global exclusions; it does not contain group names/per-group servings or ingredient-specific exclusions. Those cannot be reconstructed safely from names or assumed unchanged because an ID set is equal. Persist an immutable exact source snapshot/mapping and validate it on preview/apply/projection. Preserve protected group requirements and ingredient restrictions. A broad union is not permission to discard the original per-ingredient/group relationships. The peer confirms these details will be retained and validated in adapter snapshots. Tests must exercise a multi-group, ingredient-specific exclusion case when that adapter exists.

3. **Reviewed remaining time has a specific meaning.** `requiredLeadMinutes == nil` currently means no separately saved lead constraint; it does not make known whole remaining elapsed time unknown. `remainingElapsedMinutes` must be the user's reviewed whole remaining elapsed preparation, not inferred from active work, an absent recipe field or a zero default. Unknown remaining time must stay nil. A recorded two-hour lead can be bypassed only by explicit completed-advance-step evidence while still retaining the actual remaining time. Document this interpretation in the adapter UI and tests; no current source bug is established by the optional lead field itself.

4. **Domain data is not live authority or verified receipt evidence.** The full source/evidence event is intentionally Codable and can be constructed/imported. Structural validation cannot prove a receipt was real, that its latest usable observation was selected, that a stock origin is owned/shared, or that the actor may commit. Bind workspace/shop/actor/presentation leases and current authority again on apply and retry; durable pending writes must retain the same reviewed bytes and respect scope invalidation. The shared server must generate the supply basis from canonical observations, with availableAt at least both arrival and confirmation, and reject malformed/conflicting origin mappings. Do not expose client-provided normalized lots as authoritative shared stock.

5. **Use current projections consistently after every later evidence change.** Applying recovery does not freeze physical supply forever. Current allocation/cook views must use latest corrected/time-filtered supply and current exclusion/identity mappings, while historical events retain the evidence used at their application time. Later stock corrections and newly available deliveries must update coverage without mutating historical events or reviving superseded needs. Dinners, urgent/detail projections, reminders, next-shop, readback and recipient corrections all need the same current meal/demand version. Original order/quote/charges/receipts/templates and sent baselines remain separate and unchanged.

6. **Durability and full scope still require proof.** The test fixture constructs real domain basket/receipt/settlement values, but the engine receives only MealRecoveryState. Equality of separate fixture values proves no direct value mutation; it cannot prove app-level cross-store atomicity, selection/authority fencing, restart/save failure, Records import/export, or shared HTTP/RLS behavior. Those are the next model/service/UI tests, not reasons to weaken this increment. Existing purchase guards must remain unchanged. Local integration does not complete the required shared branch described in `authority-review/SHARED-CONTRACT.md`.

## Validation scope and next review

Existing nine tests cover the principal pure replacement/shortage/protection/replay/future-time/consent/history/unit cases. They do not yet cover a context-revision operation because no such operation is present. Preserve the frozen tested v1 inputs and add any context/provenance changes as a separately hash-bound increment with old-state decoding and stale-live-basis tests. Review the adapter against current outside-demand additions/removals, live stock corrections, source erasure and actor/selection transitions before enabling Apply.
