# Pure meal-recovery domain increment

The exact reviewed component is installed locally; see root-installation.json. The copied CoreDomain package passed **180 tests, zero failures**, including **nine new MealRecoveryTests**, with `swift test --jobs 1`. See validation.json and the exact source-manifest.json. The validation used no Xcode, simulator, app-native run or hosted mutation. Root subsequently installed the exact two tested files; application and shared-service integration remain pending. The earlier two model-test candidates for S09.03/S10.03 were preserved.

`meal-recovery-domain.patch` adds two files: MealRecovery.swift and MealRecoveryTests.swift. It changes no existing production source. Public types and initializers are in the proposed source and the tested repository-relative workspace copy. Domain values carry no authority: a live local/server adapter must authorize even an exact retry and atomically persist by CAS.

The engine stores an immutable baseline and append-only recovery events. A replacement keeps the same logical meal occurrence, uses caller-reserved new revision/demand IDs, and replaces the exact complete current target. It preserves protected ingredient snapshots, nonprotected group membership, servings, saved due/date/zone and exclusion rules. Other demands retain identity and quantities; their allocated food cannot decrease. Pinned reservation edges remain equal, using exact converted units. New pantry/receipt food is never inferred from a matching label. Supply is an explicit normalized current-observation basis with its actual availability instant.

Preview has zero mutation. It shows before/after canonical meals, needs and allocations and separate food/timing confirmation. Apply rechecks exact state, supply/reservations and the as-of allocation/timing result. A time boundary can stale a review without a source-revision change. Extra-trip/repeat consent binds the exact request; unresolved changes require explicit acknowledgment and remain short. Identical retries return the original event, while changed request or recorded review supply/reservation content under the same operation ID conflicts. Raw live evidence supplied for an already-committed retry does not create another operation.

Historical decode validates lineage, IDs, whole targets, consents, allocations and event chronology using recorded event instants, never Date(). The normalized evidence adapter still has to select the latest nonsuperseded, correctly matched receipt observation and set availableAt to at least both arrival and confirmation. The domain cannot prove raw receipt provenance from a lot value; the shared server must derive it from authoritative records.

The main fixture has a real sealed/reported16-wrap purchase, an8-wrap receipt with6usable,6Tuesday wraps,4Wednesday wraps and2protected lunches. Four separately confirmed bean portions allow only Wednesday's replacement; Tuesday remains short2, lunch stays2, and purchase/receipt/settlement/template snapshots remain exact. Additional assertions cover cancel, decode/restart, repeated replacement, old-target rejection, operation-content conflict, protected groups, deadline/exclusion preservation, other meals and pinned reservations,5portions versus4+2, future arrival, top-up shortfall, repeat consent, preparation/time boundaries, malformed lineage and exact gram/kilogram comparisons with a stealing-food rejection control.

This is **not complete S09.01 functionality or screen acceptance**. Required next increments include immutable source provenance/legacy matching, model CAS and current runtime authority, integration with live stock corrections and outside-demand changes, consistent current urgent/detail projections, Dinners/S09 routes, cook baselines/readback, reminders, next-shop, record import/export, and the shared service foundation/transaction. The current state baseline is immutable: adapters must not silently edit outsideDemands or originalMeals beneath recorded history. A recovered-calendar/date-change operation is not implemented; the replacement operation intentionally cannot extend the original deadline. No purchase guard was relaxed.

Initial scratch execution limitations are preserved in validation.json: one test-only JSON ordering comparison was corrected; a first full run lacked the two existing shared fixtures because it did not preserve repository depth. The final copy restores exact fixture paths and runs all existing tests unchanged.
