## Highest-impact concrete fix

**1. Browser editor suggestion loses its original retry envelope, and a lost response is called “Not saved.”** A user submits a correction; server commits; response drops; shopper replaces the instructions; user Refreshes and retries. `web/src/app.ts:37` retains only the key, `:80` replaces the displayed view, and `:279–282` rebuilds the POST using that new view's revision. Same key now means different canonical body and correctly gets `key_reused` (`service/src/lifecycle.ts:125–127`). No automatic retry can recover the original receipt. `uncertainSend` is only set by contributor submission, so editor failure falls through to “Not saved” (`web/src/app.ts:118`) despite a possibly committed proposal. Correction/key live only in RAM; `web/src/outbox.ts:19` accepts contributor request commands only. `web/src/api.ts:181–186` validates but discards proposal ID. Own proposal status already exists (`service/src/helper-review.ts:37`, `service/src/http.ts:127–128`). This is a demonstrable F08/E03 gap, not missing infrastructure. Existing tests `web/tests/client.test.mjs:98,203,311` cover success, receipt scope, and grant change but not lost reply + same-grant/new-revision retry. Fix: immutable reviewed body/base/key, honest uncertain state, explicit permitted storage policy, original intent retry under fresh exact grant authority, status lookup after receipt recovery. Never rebase automatically.

**2. Recipient suggestion resolution is not surfaced in browser/native recipient UX.** Backend own-proposal GET exists, but browser API drops proposal ID above; native recipient view shows only its submission receipt (`ios/Features/Household/HouseholdLifecycleViews.swift:183`). Management review is implemented. This is a useful completion of #1, not evidence that N01 own-request status is missing: contributor requests already have status, edit, withdraw, follow-up (`web/src/app.ts:229–236`). Do not conflate helper/editor suggestions with contributor requests or grant extra rights.

## Configuration / unrun acceptance — do not “fix” by bypassing gates

- **N01 invited children:** enrollment deliberately returns `consent_unavailable`, including child invitation creation (`service/src/lifecycle.ts:9,41,168`). Guardian withdrawal is implemented; verified consent-provider onboarding and child self-service deletion are not enabled. This is an incomplete launch promise if children are marketed, but requires verified guardian infrastructure/policy, not a local toggle. `service/API-PRIVACY.md:63` documents the adult-only deletion boundary.
- **D15 deletion production:** privileged provider + numeric retention policy are required; omission honestly rejects before mutation (`service/API-PRIVACY.md:67,90`). Real provider/Apple revocation, scheduled maintenance, backup purge and pre-deletion restore replay are unproven (`:114`). Reapplying the external deletion journal before serving a restored backup is an operational release prerequisite; restore tooling isn't demonstrated here. Native deletion UI is already present, so the generic “native settings integration needed” sentence in that paragraph is stale.
- **F09/P08:** deterministic receipt/coordinator tests and local StoreKit configuration do not prove App Store Connect/live purchase/restore/refund production wiring (`ios/Features/Membership/INTEGRATION.md:36`). Keep Free until configured authority validates purchases.
- **E04/F06/E10:** string catalogs/browser translations exist; human US Spanish review and actual supported mixed-phone browser acceptance remain required (`web/src/i18n.ts:1`). No claim that English/Spanish catalog presence proves human language review.
- **E07/E08/N02/N03:** package/model tests are not signed-device host sharing, lock-screen, permission denial, timezone and readback/VoiceOver acceptance (`ios/Features/DeviceSurfaces/INTEGRATION.md:30–34`). Its “root still must wire” sentence must be checked against newer composition before treating it as missing implementation. B01 accessibility belongs to parent.
