# Durable privacy journal runtime options

Prepared 2026-11-03. **Design only. No runtime adapter was installed, provider selected, credentials read, external resource created, database changed, deployment made, or production deletion enabled by this design task.** The adjacent `source-inspection.json` identifies the files inspected. These hashes describe this review, not an approved production schema/configuration or remote durability proof. The separately completed local 001–023 drill passed fifteen actual SQL/HTTP/device-inventory-wire checkpoints, using synthetic providers and the signed/fsynced local journal. It retained zero replay provider calls and `productionReady:false`. That evidence does not establish remote storage, Vercel scratch-space or independent-host disaster durability. ## Decision proposed for review

The existing trusted Node acceptance process can sign its own SQL-generated uncommitted intent and write signed records directly to a durable conditional object store. A new public acceptance service is **not inherently required**. Recommend this as the first adapter design to rehearse locally: preserve the current Vercel application shape, add a private in-process durable journal adapter, and use a separate monotonic checkpoint authority to serialize every origin across function instances. Do not implement an object-store-only adapter that relies on process memory, an expiring mutex, or a mutable `head.json` controlled by the journal writer.

This recommendation is conditional on two proofs before production consideration: the checkpoint protocol below survives concurrent/stale writers, and real bounded storage latency fits the existing request/SQL deadlines. If either remains unresolved, use the single source-agent alternative. That moves the trusted acceptance transaction and signer together to an explicitly managed Node service; it does not turn an uncommitted event into a remote generic signing request.

| Shape | Authority and storage | Main implication | Assessment |
|---|---|---|---|
| A. Vercel signer + durable records + independent checkpoint authority | The actual acceptance process signs only its SQL result. Remote storage persists signed bytes; a separate authority admits one canonical sequence/head. | Preserves current runtime shape; requires distributed conditional state, bounded calls, deployment fencing and separate observer credentials. | Recommended **local design target**, subject to the two proofs above. |
| B. One trusted source agent + durable records + independent checkpoint authority | One supervised Node service runs the actual acceptance transaction, signer and fixed-source observer. The same remote persistence protocol remains authoritative. | Reduces concurrent writer and function lifecycle problems; requires reviewed routing/authentication and service operations. | Preferred fallback if A cannot meet its timing/coordination requirements. |
| C. Stateful Node host with persistent disk + off-host durable records/checkpoint | Retains the tested fsync writer as local staging, but remote record persistence and independent head must finish before returning from either journal phase. | Close to the existing writer, with explicit single-instance/failover operations; local disk alone does not satisfy the disaster boundary. | Practical alternative when stateful hosting is already owned and approved. |

S3 Standard is one researched record-store example, with strongly consistent reads and conditional writes; DynamoDB conditional/transactional writes are one researched mechanism for the checkpoint authority. These are examples of capabilities, not a provider choice or an assertion that a table/bucket alone implements the protocol. S3 documents Standard as storing across at least three Availability Zones, with a designed durability figure rather than an unconditional guarantee. [S3 consistency](https://aws.amazon.com/s3/consistency/), [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html), [DynamoDB conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html), [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).

A persistent-disk service is also technically available: Render documents persistent mounts, restricted to one running service instance, with deploy downtime and no horizontal scaling for that disk. Snapshot restoration loses changes after the snapshot, so snapshots cannot acknowledge this journal's latest head. This describes option C's operational tradeoff; it is not a recommendation to buy Render. [Render disks](https://render.com/docs/disks).

## Source-specific facts and preserved boundaries

- `service/src/privacy-journal.ts:18` defines the injected `configurationId`, `beforeCommit(event)`, `afterCommit(eventId)` and `acknowledgeJob(jobId)` port. The local implementation uses owner-only files, an exclusive local lock and a process queue. These coordinate one local writer, not independent function instances.
- `service/src/privacy.ts:67` runs recent signed authentication, exact live session and provider availability checks before acceptance. At lines 72–75 the application obtains the SQL-produced event inside its open application-role transaction, waits for `beforeCommit`, commits, and waits for `afterCommit`. The provider, numeric policy and journal remain jointly required. An intent alone never authorizes replay or worker eligibility.
- `service/migrations/022_privacy_journal.sql:134` resolves targets/effects under SQL locks and emits the private immutable outbox row. The separate source observer cannot see a newly emitted row until that transaction commits. `privacy_journal_acknowledge` is private owner authority; its arguments are trusted proof supplied by the exporter, **not SQL verification of an external signature or checkpoint**.
- The local writer resolves committed payloads from its fixed source (`privacy-journal.ts:145`), checkpoints before SQL acknowledgement, and acknowledges the exact commit record's sequence/hash. Later heads must not change that acknowledgement identity. Acknowledgement may refer to a commit record covered by a later verified head.
- Ordinary claim requires acknowledged acceptance and all previous job events. Target progress must be acknowledged before a provider call; completion must be acknowledged before complete status/cleanup. The remote adapter must preserve these SQL and service boundaries.
- `service/src/runtime.ts:80` currently constructs `new PrivacyService(repository)` without provider, policy or journal. `operations-runtime.ts` invokes `privacy.cleanup()` only and reports `privacyJobProcessingEnabled:false`. This design changes neither default.
- `vercel.json` pins `pdx1`, API maximum duration 30 seconds and maintenance maximum duration 60 seconds. The Node server sets `requestTimeout=15000`. Each journal phase currently races a **non-cancelling** 5-second timer; acceptance SQL sets statement/lock/idle-transaction timeouts of 10/2/7 seconds. A 30-second function limit does not prove the complete request fits the 15-second application budget.

Vercel documents a read-only filesystem with writable `/tmp` scratch space. Treat that scratch space, module globals and function lifetime as caches only. `waitUntil` remains bounded by function lifetime and is not durable work execution. No filesystem adapter using `/tmp`, or response-first background append, meets this port. [Vercel runtimes](https://vercel.com/docs/functions/runtimes), [function lifecycle](https://vercel.com/docs/functions), [waitUntil lifetime](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package).

## Signing authority: the uncommitted intent case

For A, keep the signer in the same trusted server process/closure as the actual SQL callback. It accepts the returned `PrivacyJournalEvent` only through that internal port call after the ordinary service gates; it does not expose a network signing route. The record store accepts already signed canonical bytes and cannot create a signature. The checkpoint authority verifies records and advances a head; it cannot invent an accepted target or supply a signing key.

It is impossible for a separate SQL reader to independently confirm this newly created intent before COMMIT under the current contract. A digest, authenticated transport or a request saying `authorized:true` does not cure that visibility limit. The approved trust boundary is the acceptance service receiving its own SQL result. The intent remains uncommitted quarantine evidence until the fixed-source observer obtains the exact immutable committed outbox row and matching digest. A later committed-row lookup cannot authorize an acceptance lacking its original durable intent.

For B, move that actual acceptance transaction with the signer. Either host the relevant existing service path there, or define a normal authenticated deletion request boundary with the full current verifier/provider/policy/session checks there. A Vercel proxy cannot grant authority with forwarded identity headers or prechecked Booleans. Do not send arbitrary candidate events/target lists to a remote signing endpoint. Routing and auth changes would be separately reviewable implementation work.

This retains the existing explicit trust in source owner, signer and host owner. It does not claim resistance to compromise of those trusted components.

## Canonical log, serialization and independent head

Separate **record storage** from **checkpoint authority**. The writer can create immutable record objects and request admission; it cannot overwrite/delete objects, set arbitrary checkpoint state, reset genesis, shorten a head or clear a fence. The checkpoint authority has its own fixed identity, policy and operator recovery access, a strongly consistent current state, and independently retained head history. The application has no direct table/object write credential for that state. Separate directories or two objects using one unrestricted writer credential do not establish this authority boundary. Same-provider storage can meet a host-loss boundary; a separate account/provider is an additional failure/control-plane boundary to decide explicitly.

The authority maintains an atomic state per pinned origin: `(lineage, schemaDigest, configurationId, keyId/public-key fingerprint, generation, mode, seq, hash, pendingOperation)` plus event transition/idempotency indexes. Modes are `active`, `pending`, `recovery`, `sealed`. Generation is monotonically increasing; a source SQL fence is separately monotonic and is never represented by a lease expiry.

1. The trusted signer obtains the current independently authenticated head and generation. It validates the supported strict content-free payload schemas and exact source pins, then creates the next v1 signed record. The current canonical format, Ed25519 signature, event digest, previous hash and sequence remain unchanged.
2. `reserve` atomically compares generation/mode/exact previous head, reserves the next sequence for one operation and binds its record hash/length, event ID/digest/kind/job dependency and a short authority-clock deadline. A conflicting operation must fail or wait within its own bounded call; it must not choose another sequence from a process cache. An active pending slot is never stolen merely because a wall-clock lease expired.
3. The writer conditionally creates an object under the ticket/record hash and verifies exact stored bytes/checksum/version. Object keys and metadata use opaque origin/configuration hashes, sequence and record digest, with no raw identity, email, token or grocery content. The v1 record is the only event content. Retries can accept a pre-existing object only after exact-byte verification, never after treating a conflict response as success.
4. `publish` makes the authority read the exact object version, verify canonical bytes/signature/schema/pins/transition and compare the still-current ticket/generation/deadline. It atomically advances the head and event/idempotency state, retains a head receipt, and clears the pending slot. Only its authenticated durable receipt completes the port phase. A receipt for a different record, stale head or different origin is rejected.
5. A stale worker may finish an old object PUT after timeout or fencing. Its object is an **unreferenced blob**, never the canonical log: the old ticket cannot publish after its generation/deadline loses authority. Epoch checks stored in a different system cannot stop an already in-flight PUT; this is why the immutable object namespace alone is not the canonical sequence. Export follows the independently admitted exact record references through the pinned head, not bucket listing order or the greatest available sequence.

S3 `If-None-Match:*` is create-if-absent against the current object version, and `If-Match` compares an ETag. It is not a cross-system fencing token and ETag is not the journal's cryptographic digest. Deny delete/delete-marker operations to normal writers; versioning/Object Lock alone does not prohibit creation of another version or establish which version is canonical. DynamoDB reads must explicitly request strong consistency on the base table when observing checkpoint state; default eventual reads or a global secondary index are insufficient. [S3 conditional behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [DynamoDB consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html).

Object Lock could protect retained record versions after a reviewed retention decision. Compliance retention cannot be shortened, including by the account root, so it must not be enabled as an implementation default or substitute for approved privacy/backup retention. [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html), [retention modes](https://aws.amazon.com/s3/features/object-lock/).

## Exact port work and deadline semantics

The application-facing port can keep the same three operations and configuration ID. Production implementation needs a call context (`attemptId`, shared absolute request deadline, `AbortSignal`) and a verified receipt result internally. The acceptance path must pass a call-owned deadline rather than racing an unowned promise. The adapter owns storage requests and SQL observation/acknowledgement; no detached promise is allowed to decide a later COMMIT. Its constructor pins source identity, record-store identity/namespace, checkpoint-authority identity, deployment principal, signing key and configuration; no caller may override them per event.

`beforeCommit` returns only after both durable intent storage and admitted checkpoint receipt. The service checks that its deadline remains valid immediately before issuing COMMIT. If the phase fails/times out, the service rolls back its transaction; a late durable intent is unresolved quarantine evidence and must never be upgraded by client input. `afterCommit` accepts only event ID, reads the exact committed fixed-source row, verifies its original durable intent and digest, admits the commit observation/head, then acknowledges SQL with the **commit record** sequence/hash. `acknowledgeJob` takes only job ID and derives unacknowledged events from that same fixed source in dependency order.

Reserve/publish use authority deadlines shorter than the enclosing 5-second phase; exact values require measured latency and SQL commit margin, not a claim that the network always meets them. Avoid waiting for a distributed lock while holding acceptance locks. Derive one end-to-end request deadline before provider/DB work and refuse work with insufficient remaining budget. Do not simply increase transaction timeouts or function duration to conceal unbounded retries. The existing 7-second idle transaction timeout remains a rollback safeguard; connection cancellation/timeouts do not prove whether a COMMIT or an already-sent acknowledgement executed.

`AbortSignal` requests cancellation; it does not undo a remote operation already accepted. On any ambiguous record/head outcome the adapter is locally poisoned and the persisted pending operation prevents new origin transitions; if persisting an explicit blocked state also fails, the existing reservation remains blocking. A deadline-aware authority rejects late publication. There is no automatic lease takeover or head reset. A crash after successful publish but before its response can leave an admitted unresolved intent; recovery must inspect the exact operation and source.

The proposed abort-aware adapter stops initiating new acknowledgements after its caller aborts. An acknowledgement sent just before timeout may already execute despite cancellation. That is an ambiguous SQL result to reconcile from the fixed source, not permission to assume rollback. It cannot be sent until the exact committed observation and independent head are already durable. **The existing approved contract permits safely durable late acknowledgement and worker eligibility after a failed HTTP response; the original client-held status capability provides recovery.** There is no false 202, and the response must never promise that failure means no job exists. A stricter “no worker eligibility after response timeout” rule would be an **optional new product contract**, not a required guard or blocker for this approved design. The current SQL ack signature cannot enforce that optional rule; adopting it would require a separately reviewed SQL deadline/generation guard and worker coordination.

For normal operation, safe retries of a completed operation reuse its exact admitted record/receipt. An unknown/pending/expired operation does not retry by allocating a new branch. Full explicit fenced recovery handles uncertainty, retaining the conservative existing local failure semantics.

## Fencing, recovery and restore compatibility

Operator recovery first closes ordinary checkpoint admission/increments generation, blocking all old tickets. It then commits `UPDATE ritc.privacy_journal_origin SET fenced=true WHERE singleton` against the fixed source. The SQL SHARE-lock boundary must finish waiting for earlier acceptance/progress transactions; only afterward can source absence resolve an intent as rollback. In-flight old PUTs remain inert because old generations cannot publish.

Recovery resolves admitted/tail operations against the exact immutable committed source rows; it retains and acknowledges committed observations and appends rollback only for proven absent source events after the SQL fence. Unknown source, mismatched digest, conflicting object or incomplete head remains quarantined. Only the recovery principal can admit rollback/final sealing. Once all intents/transitions are resolved, the independent authority seals the exact final `fenced:true` v1 head. The existing source fence is terminal for that lineage; this design does not silently un-fence it or rotate origins to escape an unresolved tail.

Export materializes the exact existing v1 canonical NDJSON and independently supplied `PrivacyJournalHead`; storage tickets/generations/receipts stay outside the strict v1 records. Existing complete-chain and final-head verification stays mandatory, including absent suffix/early-prefix rejection, all signatures and strict restore event validation. Recovery/restore tooling remains owner-only quarantine work, never a public import path. Preserve the existing 10,000-record/32-MiB limits until an explicit coverage/segmentation design is approved; do not silently rotate or compact to avoid capacity failure.

## Credentials, source pins and implementation touch points

Production credentials must keep the private signing key outside PostgreSQL, dumps, evidence, build output and `/tmp`. Option A can load an Ed25519 key into process memory from explicitly scoped runtime secret custody; sensitive Vercel variables are one available mechanism, not proof of protection from the trusted runtime itself. Environment changes apply to new deployments, so old deployments must also lose checkpoint authorization through generation/deployment-principal fencing. Preview deployments must never receive the production signer/source/namespace identity. Vercel documents these environment mechanics. [Sensitive variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables), [environment changes](https://vercel.com/docs/environment-variables).

Pin exact source endpoint/TLS trust, database identity and immutable origin; schema/build manifest digest; provider/issuer/policy configuration identity; Ed25519 key ID/public fingerprint; durable store namespace; checkpoint authority identity and recovery principal. A URL alone, a digest supplied by the bundle or a mutable ambient environment flag cannot establish those pins. V1 currently pins a single key: key rotation requires an approved continuity/lineage plan, not replacing the trusted key in place. Keep encryption-key recoverability separate from signing-key custody.

Current local owner-pool access is an explicit trust boundary, not a production credential recommendation. A future production observer should get only dedicated fixed-source origin/committed-event/unacknowledged-event reads and acknowledgement execution through restricted functions. No raw journal tables, target/import/plan/receipt writes, source fence ability, or signing key for ordinary app/worker roles. New narrow read/ack functions and their role grants require a separately reviewed migration; this task does not grant them. Recovery fence authority stays separate.

## Prerequisites and local acceptance cases

No external setup is needed to decide the next local work. Parent review should select A's coordinator/transport contract or B's routing boundary, approve a limited local adapter implementation lane, and keep production disabled. Before any later external action, the owner must select the storage/checkpoint/service provider and failure boundary, region/data residency, secret/recovery custody, retention/backup coverage, operational recovery owner and budget. Provider selection and a budget based on the chosen region, traffic, retention and service shape are future decisions; this design assumes no prices or free-tier coverage. Real deletion provider/Apple handling and numeric retention policy remain independent gates.

The next useful local adapter rehearsal is a provider-neutral deterministic fake transport with real canonical/signature verification and enforced reserve/publish CAS, not a successful no-op port. Required cases are two concurrent instances reserving one head; duplicated event/different digest; duplicate committed observation using the same ack; delayed old PUT after generation fence; publication rejected after authority deadline; crash at reserve/PUT/publish/SQL COMMIT/ack; lost success response; pending state surviving a new process; stale independent head; unacknowledged progress blocking provider calls; SQL fencing waiting for earlier transactions; and strict full-chain restore from admitted references. It must show no COMMIT after failed intent phase, no acknowledgement before durable commit+head, no arbitrary-target signing/import, and zero real provider calls.

Only after that local contract passes should a selected provider adapter be authored/reviewed and an explicitly approved isolated remote rehearsal measure cold start, contention and tail latency against the 5/7/15-second constraints. Neither this design nor the earlier fsync drill supplies those remote results.
