## Exact boundaries

`PrivacyJournalPort` is an injected trusted local writer/exporter. `PrivacyService` retains recent signed authentication, exact live provider session, numeric policy and provider availability gates. A missing port rejects deletion before acceptance; no default journal, signing key, production policy or provider is supplied. Preview reports deletion available only with all three dependencies.

The application transaction calls `ritc.privacy_journal_request(text,text,uuid,uuid,text,text,jsonb,integer,integer,jsonb) RETURNS jsonb`. Its final JSON argument is the service's bounded gate attestation (configuration ID, recent authentication time, hashed exact session binding, checked-at time). It is bound into the SQL-produced immutable event. SQL preserves the old authority checks; attestation is trusted service evidence, not a new SQL proof of JWT/provider availability. The old `privacy_request` implementation becomes private. The port sees only the SQL-produced event from that open transaction, durably appends intent, and fsyncs journal+directory before COMMIT. Then its separate owner source connection resolves that event ID from committed private outbox, matches the digest, durably appends commit observation, and atomically replaces/fsyncs a separate checkpoint before owner-only SQL acknowledgement. Only then may the service return 202 or the worker claim it. Any ambiguous commit or unresolved intent prevents fenced-head verification. A lost response is recovered with the existing retained client status capability; plaintext capability is never exported.

Private capture stores one immutable origin (lineage, schema/config IDs), immutable outbox payload and digest, target pairs/digests, and separate acknowledgement. No private key enters PostgreSQL. Outbox has no cascading FK to ephemeral jobs. No app/worker raw capture/ack/plan/receipt privileges or import/export helper execution. The owner exporter accepts an event ID and resolves the payload from its fixed source; there is no sign-JSON or target-list signing interface.

Capture obtains identity advisory and ordered household locks before the old acceptance call. A bounded snapshot contains only whitelisted IDs, state/organizer/contribution flags, responsibility fields, revocation times, hashes of identity/guardian evidence, and retired purchase hashes. No labels, grocery text, email, JWTs, receipt plaintext, device/session secrets or raw purchase IDs. The acceptance event stores the actual changed before/after tuples, exact target bindings and original persisted job deadlines/policy/hash. Restores require these exact tuples; older incompatible backups remain quarantined. Existing 021 triggers remain active and their required state projection must be added once that migration is stable.

## Restore SQL signatures and receipts

Owner-only `privacy_restore_register(run_id uuid, destination_oid oid, bundle_digest text, pinned_head jsonb, events jsonb) RETURNS uuid` is called only after local CLI verification of pinned key/config/lineage/schema, the complete canonical signature/hash chain, final independently supplied fenced head, intent/commit resolution, dump manifest and explicit newly owned quarantine DB/OID. Node verification remains an explicit owner trust boundary; SQL does not claim to verify Ed25519. Registration validates every target binding and every recorded before/after tuple before any mutation, rejects existing/conflicting jobs, stages original job IDs/markers/present target pairs, and records absent exact pairs separately. No fabricated members or inferred wider identity search.

`privacy_restore_claim(run_id uuid, worker_lease uuid) RETURNS uuid` and `privacy_restore_erase_next(run_id uuid, job_id uuid, worker_lease uuid) RETURNS jsonb` are the only new worker restore functions. The worker supplies a verified persisted run ID and lease, never a target. Claim excludes ordinary source jobs; ordinary claim/finish exclude replay jobs. Each erase-next locks the plan/job/next registered target, verifies the live exact lease and acceptance/target digests, calls the existing full `privacy_erase_target` chain, and inserts the per-target receipt before that same transaction commits. Unique `(acceptance_event,household,member)` receipts bind the digest across repeat runs; same ID with another digest errors. Missing rows receive `absent_no_effect` receipts without invoking the eraser. Committed receipts skip subsequent calls so revision-changing extensions do not run twice. A failure before COMMIT rolls back erasure+receipt together. A failure after COMMIT resumes from receipt.

Replay deletes restored browser credential rows by the original adult identity hash and imports only exact source retired-purchase hashes. It never calls a provider or `privacy_finish(...,true,...)`. It records local application erasure and historical source observations separately; replay jobs/public status remain pending with `provider_erased_at/completed_at NULL`. A completed plan permits a local synthetic probe only; it is not a deployment gate.

Source erase/finish wrappers append immutable progress events in their transactions. Source claim requires acknowledged acceptance and all prior transitions. Provider deletion occurs only after the target events have been exported/acknowledged. Completion status/cleanup is blocked until the completion event has its durable independent-head acknowledgement. Scheduled operations remains cleanup-only.
