## Ranked independent user-visible gaps

1. **S07 pending store offers:** strongest narrow target. Opening existing saved offer does not provide an edit/review action, and a new screen's operation identity is unrelated to existing saved offers. Manual price and ceiling are displayed/copyable but never assessed. Contract lines43–47 vs `PickupArrivalView.swift:106`–168 and `PickupModel.swift:74`–88. Recommended first fix: identity-safe reopen/edit with original record/journey revision guards plus truthful price-ceiling assessment; keep full combined-price/meal acceptance as separate remaining scope.
2. **S22 contributor structured review:** request is sent directly from item/quantity fields, without captured-original/parsed-field review. Contract123 vs `HouseholdSettingsView.swift:88`–95. Can be fixed with an explicit own-request review surface reusing capture components and maintaining author-only payload, but requires more than a cosmetic button.
3. **S10/S20 live-view navigation:** static handoff is fully reachable; live-view composer exists elsewhere but no distinct current-view choice in cook flow and no Records→Manage shared views shortcut. Contract57–61/111 vs `PickupRepairView.swift:225`–261 and `RoomInTheCartApp.swift:204`–240, with actual managed-view alternative at `HouseholdSettingsView.swift:60`. Link/entry integration is bounded, though prefilling private source fields requires explicit review.
4. **E06 stock maintenance across S04/S09:** confirmed lots can be added but existing pantry/freezer lots have no visible correction/remove/use-first/storage-date editor. Contract159 vs `PickupRepairView.swift:137`–187 inspected. This is not resolved by having allocation math alone. Model audit owns deeper storage checks.
5. **Navigation contract polish:** S01→inbox, S12→reuse dinner, S05→two quotes, and specified sheet-vs-push differences. These are reachable capabilities with missing contextual entries, not fully absent screens. Global selection/root accessibility/planner are parent-owned.

## S07 minimal implementation plan (not a claim of full completion)

- Existing domain helpers: `Checkout.replacementCeiling` (`ios/Packages/CoreDomain/Sources/CoreDomain/Checkout.swift:219`) computes an offer ceiling from explicit remaining allowance; `RetailerDeadline` (`Pickup.swift:471`) preserves cutoff status; `Quantity`/`Money`/`CostEvidence` preserve unknown vs exact/bounded facts. No complete dish-specific offer evaluator is currently called by `PickupOfferView`.
- Add focused offer editor opening either `.new` or one stable offerID; retain selected journeyID and original saved offer/revision. Never initialize a new ID when reopening an existing row.
- Stage review before commit. In model mutation verify same journey and unchanged original saved offer (and relevant source revision) before replacing precisely that record. Leave draft intact if stale. Persist new ID exactly once; explicit new-offer action resets it.
- Preserve `.bounded` and `.unknown` evidence exactly when opened unchanged; avoid converting the preexisting evidence to a single optional amount. Represent amount/reason/range explicitly in draft or hold original unchanged unless edited.
- Render remaining original quantity, required amount, linked need names/exclusions and safe ceiling comparison (below/at/above/unknown). Unknown/bounded result remains conditional. Never label complete checkout fit, meal feasibility, retailer acceptance, actual fill or price verification from these inputs.
- Preserve cutoff→Await pickup, household preference vs retailer response, existing private scoped note copy and copy event behavior. Reopening/editing must not create new delivery/charge/placement facts.
- Regressions: reopen/correct same ID; second unrelated record untouched; stale journey/revision refusal; exact bounded/unknown roundtrip; cutoff retained; ceiling over/unknown; note copy contains no household cap/private names. Add UI selectors for saved-offer editor/review/commit and a narrow native reopen test if the current harness can launch a stable fixture.
