# Committed deletion source on Vercel

Use a dedicated protected project with root directory `source-gateway-vercel`. Enable the build setting that includes files outside the root. Use Node.js 22 and the region of the application database. Build using the [existing standalone deployment procedure](../journal-vercel/README.md#project-settings), and verify that the output includes the compiled source adapter, keeps raw request streams and maps `POST /v1/source` to the function. The source gateway uses the application database, while the separate journal authority retains the independently signed receipts.

Keep `JOURNAL_SOURCE_GATEWAY_JSON` in the gateway project's sensitive production environment. It contains the existing durable `pins`, the authority's public SPKI PEM as `authorityPublicKey`, independent random 32-byte base64url `applicationToken` and `operationsToken`, and `observer`. Configure the observer's `connection` with the gateway's restricted PostgreSQL login, password, database, port and verified TLS CA/servername. Set `databaseOid`, `observerRole`, `observerRoleOid`, `ownerRole`, and `ownerRoleOid` from the provisioned source. The gateway needs only public verification material from the journal authority.

In each caller's `PRIVACY_DELETION_JSON`, set `observer` to an object with `mode` equal to `gateway`, the stable HTTPS `origin`, that caller's `token`, `vercelTrustedSource` equal to `true`, and the fixed `database`, `databaseOid` and `observerRoleOid`. Configure Vercel Deployment Protection on all deployments and allow the two production workloads as Trusted Sources. The client sends its Vercel workload token as well as the scoped bearer. Keep the direct database observer configuration for installations using the previously supported direct source.

For a read-only connectivity check, send the fixed `origin` operation through an authorized caller. The request envelope includes version 1, a fresh random UUID `requestId`, the current `scopeDigest`, `databaseBinding`, the parent `attemptId`, `deadlineUnixMs`, and `command: {"action":"origin"}`. The client checks the echoed request ID and source binding on every response. Its success verifies the registered committed source and the database capability checks. Reads return committed data only. An acknowledgement requires the exact signed commit receipt. A dropped response can follow a committed acknowledgement, so retry with the same receipt and check the retained journal.
